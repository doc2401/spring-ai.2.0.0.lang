    OpenAI 聊天

    Spring AI 支持来自 OpenAI 的多种人工智能语言模型，该公司是 ChatGPT 背后的开发团队。凭借其创建行业领先的文本生成模型和嵌入技术，OpenAI 在激发人们对 AI 驱动文本生成的兴趣方面发挥了关键作用。

    自版本2.0.0-M5起，Spring AI 在底层使用官方的openai-java SDK 来处理所有 OpenAI 模型。此次过渡预计将无缝进行，且对现有使用 OpenAI API 属性和构建器的用户而言不会有任何破坏性变更。如果您发现任何问题，请通过Spring AI GitHub Issues向我们报告。

    Prerequisites

    您需要创建一个与 OpenAI 的 API，以访问 ChatGPT 模型。

    在OpenAI 注册页面创建账户，并在API 密钥页面生成令牌。

    Spring AI 项目定义了一个名为 spring.ai.openai.api-key 的配置属性，您应将其设置为从 openai.com 获取的API Key的值。

    您可以在 application.properties 文件中设置此配置属性：

    spring.ai.openai.api-key=<your-openai-api-key>

    为在处理敏感信息（如 API 密钥）时增强安全性，您可以使用 Spring 表达式语言（SpEL）来引用自定义环境变量：

    # In application.yml
spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
    # In your environment or .env file
export OPENAI_API_KEY=<your-openai-api-key>

    您也可以在应用程序代码中通过编程方式设置此配置：

    // Retrieve API key from a secure source or environment variable
String apiKey = System.getenv("OPENAI_API_KEY");

    添加仓库和物料清单

    Spring AI 的构件发布在 Maven Central 和 Spring Snapshot 仓库中。请参考构件仓库部分，以将这些仓库添加到您的构建系统中。

    为便于依赖管理，Spring AI 提供了一个 BOM（物料清单），以确保整个项目中使用的 Spring AI 版本保持一致。请参考依赖管理部分，将 Spring AI BOM 添加到您的构建系统中。

    Auto-configuration

    Spring AI 的自动配置中，starter 模块的构件名称已发生重大变更。 有关更多信息，请参阅升级说明。

    Spring AI 为 OpenAI 聊天客户端提供了 Spring Boot 自动配置功能。 要在项目的 Maven `pom.xml` 或 Gradle `build.gradle` 构建文件中启用它，请添加以下依赖：

    • Maven

    • Gradle

    <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>
    dependencies {
    implementation 'org.springframework.ai:spring-ai-starter-model-openai'
}
    请参考依赖管理部分，将 Spring AI BOM 添加到您的构建文件中。

    聊天属性

    重试属性

    前缀 `spring.ai.retry` 用作属性前缀，允许您为 OpenAI 聊天模型配置重试机制。

    Property Description Default

    spring.ai.retry.max-attempts

    最大重试尝试次数。

    10

    spring.ai.retry.backoff.initial-interval

    指数退避策略的初始睡眠时长。

    2 秒。

    spring.ai.retry.backoff.multiplier

    退避间隔倍数。

    5

    spring.ai.retry.backoff.max-interval

    最大退避时长。

    3 分钟。

    spring.ai.retry.on-client-errors

    如果为假，则抛出 NonTransientAiException 异常，并且不要针对 `4xx` 客户端错误代码进行重试。

    false

    spring.ai.retry.exclude-on-http-codes

    不应触发重试的 HTTP 状态码列表（例如，用于抛出 NonTransientAiException）。

    empty

    spring.ai.retry.on-http-codes

    应触发重试的 HTTP 状态码列表（例如，用于抛出 TransientAiException）。

    empty

    连接属性

    spring.ai.openai 前缀用作连接 OpenAI 的属性前缀。

    Property Description Default

    spring.ai.openai.base-url

    连接使用的 URL

    api.openai.com

    spring.ai.openai.api-key

    API 密钥

    -

    spring.ai.openai.organization-id

    可选地，您可以指定用于 API 请求的组织。

    -

    spring.ai.openai.project-id

    可选地，您可以指定用于 API 请求的项目。

    -
    对于属于多个组织（或通过其旧版用户 API 密钥访问项目）的用户，您可以选择性地指定用于 API 请求的组织及项目。 这些 API 请求的使用量将计入所指定的组织和项目的用量。

    User-Agent 标头

    Spring AI 会自动向所有发送至 OpenAI 的请求添加 User-Agent: spring-ai 请求头。 这有助于 OpenAI 识别源自 Spring AI 的请求，以便进行分析和提供支持。 该请求头由 Spring AI 自动发送，无需用户进行任何配置。

    如果您是一个提供 API 并构建兼容 OpenAI 服务的供应商，可以通过读取服务器接收请求中的 `User-Agent` HTTP 标头来追踪 Spring AI 的使用情况。

    配置属性

    启用和禁用聊天自动配置现在通过带有前缀spring.ai.model.chat的顶层属性进行配置。

    要启用该功能，请设置 spring.ai.model.chat=openai（默认已启用）。

    要禁用该功能，请将 spring.ai.model.chat 设置为 none（或任何不等于 openai 的值）。

    此更改旨在支持配置多个模型。

    spring.ai.openai.chat 前缀是用于配置 OpenAI 聊天模型实现的属性前缀。

    Property Description Default

    spring.ai.openai.chat.enabled（已移除且不再有效）

    启用 OpenAI 聊天模型。

    true

    spring.ai.model.chat

    启用 OpenAI 聊天模型。

    openai

    spring.ai.openai.chat.base-url

    可选覆盖项，用于为 `spring.ai.openai.base-url` 属性提供专用的聊天接口 URL。

    -

    spring.ai.openai.chat.api-key

    可选覆盖项，用于为 `spring.ai.openai.api-key` 提供专用的聊天 API 密钥。

    -

    spring.ai.openai.chat.organization-id

    可选地，您可以指定用于 API 请求的组织。

    -

    spring.ai.openai.chat.project-id

    可选地，您可以指定用于 API 请求的项目。

    -

    spring.ai.openai.chat.model

    要使用的 OpenAI 聊天模型名称。您可以选择以下模型：`gpt-5-mini`、`gpt-4o`、`gpt-4o-mini`、`gpt-4-turbo`、`gpt-3.5-turbo` 等。有关更多信息，请参阅模型页面。

    gpt-5-mini

    spring.ai.openai.chat.temperature

    用于控制生成补全结果表面创造力的采样温度。较高的值会使输出更加随机，而较低的值则使结果更加聚焦和确定性。不建议对同一补全请求同时修改 temperature 和 top_p，因为这两个设置的交互作用难以预测。

    0.8

    spring.ai.openai.chat.frequency-penalty

    介于 -2.0 和 2.0 之间的数字。正值会根据文本中现有 token 的频率对新 token 进行惩罚，从而降低模型逐字重复相同内容的概率。

    0.0f

    spring.ai.openai.chat.logit-bias

    调整指定 token 在补全中出现的概率。

    -

    spring.ai.openai.chat.max-tokens

    生成聊天补全时允许生成的最大 token 数量。输入 token 和生成 token 的总长度受模型上下文长度的限制。适用于非推理模型（例如 gpt-4o、gpt-3.5-turbo）。不能与推理模型一起使用（例如 o1、o3、o4-mini 系列）。与 maxCompletionTokens 互斥——同时设置两者将导致 API 错误。

    -

    spring.ai.openai.chat.max-completion-tokens

    完成时可生成的 token 数量的上限，包括可见输出 token 和推理 token。推理模型必需（例如 o1、o3、o4-mini 系列）。不可与非推理模型配合使用（例如 gpt-4o、gpt-3.5-turbo）。与 maxTokens 互斥——同时设置两者将导致 API 错误。

    -

    spring.ai.openai.chat.n

    为每个输入消息生成的聊天完成选项数量。请注意，您将根据所有选项中生成的 token 总数被收费。请将 n 保持为 1 以最小化成本。

    1

    spring.ai.openai.chat.store

    是否存储此聊天完成请求的输出以供我们的模型使用

    false

    spring.ai.openai.chat.metadata

    开发者定义的用于在聊天补全仪表板中过滤补全结果的标签和值。

    空地图

    spring.ai.openai.chat.output-modalities

    您希望模型为此请求生成的输出类型。大多数模型能够生成文本，这是默认选项。gpt-audio 模型还可以用于生成音频。若要请求该模型同时生成文本和音频响应，您可以使用：text、audio。此功能不支持流式传输。

    -

    spring.ai.openai.chat.output-audio

    音频生成参数。当请求的音频输出模态包含 `output-modalities` 中的 `audio` 时，此参数为必需项。该功能需要 `gpt-audio` 模型支持，且不支持流式完成。

    -

    spring.ai.openai.chat.presence-penalty

    -2.0 到 2.0 之间的数字。正值会根据新词是否出现在当前文本中对其进行惩罚，从而提高模型讨论新话题的可能性。

    -

    spring.ai.openai.chat.response-format.type

    兼容GPT-4o、GPT-4o mini、GPT-4 Turbo以及所有晚于gpt-3.5-turbo-1106的GPT-3.5 Turbo模型。JSON_OBJECT类型启用 JSON 模式，确保模型生成的消息为有效的 JSON。 JSON_SCHEMA类型启用结构化输出，确保模型输出符合您提供的 JSON Schema。使用JSON_SCHEMA类型时，还需设置responseFormat.schema属性。

    -

    spring.ai.openai.chat.response-format.name

    响应格式架构名称。仅适用于 `responseFormat.type=JSON_SCHEMA`

    custom_schema

    spring.ai.openai.chat.response-format.schema

    ```json { "schema": { "type": "object", "properties": { "message": { "type": "string", "description": "响应格式为 JSON Schema，仅适用于 responseFormat.type=JSON_SCHEMA" } }, "required": ["message"] } } ```

    -

    spring.ai.openai.chat.response-format.strict

    响应格式 JSON 架构遵循严格性。仅适用于 `responseFormat.type=JSON_SCHEMA`。

    -

    spring.ai.openai.chat.seed

    此功能处于测试版。如果指定了种子值，我们的系统将尽最大努力进行确定性采样，确保使用相同种子和参数的重复请求返回相同结果。

    -

    spring.ai.openai.chat.stop

    最多 4 个序列，在此序列中 API 将停止生成更多 token。

    -

    spring.ai.openai.chat.top-p

    另一种替代温度采样的方法是核采样（nucleus sampling），其中模型会考虑概率质量在top_p范围内的 token 结果。例如，0.1 表示仅考虑占据前 10% 概率质量的 token。我们通常建议调整此参数或temperature，但不要同时调整两者。

    -

    spring.ai.openai.chat.tools

    模型可能调用的工具列表。目前仅支持函数作为工具。使用此功能提供模型可生成 JSON 输入的函数列表。

    -

    spring.ai.openai.chat.tool-choice

    控制模型调用哪个（如果有）函数。none 表示模型不会调用函数，而是生成一条消息。auto 表示模型可以在生成消息或调用函数之间进行选择。通过指定特定函数 {"type": "function", "function": {"name": "my_function"}} 会强制模型调用该函数。如果没有定义函数，默认值为 none；如果定义了函数，默认值为 auto。

    -

    spring.ai.openai.chat.user

    代表您最终用户的唯一标识符，有助于 OpenAI 监控和检测滥用行为。

    -

    spring.ai.openai.chat.stream-usage

    （仅适用于流式传输）设置为添加一个包含整个请求的令牌使用统计信息的额外块。此块的choices字段为空数组，而所有其他块也将包含一个使用字段，但其值为 null。

    false

    spring.ai.openai.chat.parallel-tool-calls

    在工具使用期间是否启用并行函数调用。

    true

    spring.ai.openai.chat.prompt-cache-key

    OpenAI 用于优化相似请求缓存命中率的缓存键。可改善延迟并降低成本，已取代用于缓存目的的废弃 `user` 字段。了解更多。

    -

    spring.ai.openai.chat.safety-identifier

    一个稳定的标识符，用于帮助 OpenAI 检测违反使用策略的用户。应为一个哈希值（例如哈希后的用户名或电子邮件）。该字段替代了已弃用的 user 字段，以支持安全追踪。了解更多。

    -

    spring.ai.openai.chat.http-headers

    可选的 HTTP 头，将添加到聊天完成请求中。若要覆盖 `api-key`，需要使用 `Authorization` 头键，并且必须在密钥值前添加 `Bearer` 前缀。

    -

    spring.ai.openai.chat.tool-callbacks

    用于与 ChatModel 注册的回调工具。

    -

    spring.ai.openai.chat.service-tier

    指定用于处理请求的处理类型。

    -

    spring.ai.openai.chat.extra-body

    请求中需包含的额外参数。接受任何键值对，这些键值对将被扁平化到 JSON 请求的顶层。专为支持超出标准 OpenAI API 参数的 OpenAI 兼容服务器（如 vLLM、Ollama 等）设计。官方 OpenAI API 会因未知参数而返回 400 错误。有关详细信息，请参阅使用额外参数与 OpenAI 兼容服务器。

    -

    在使用暴露 OpenAI 兼容 API 的本地 Docker Model Runner 时，如果服务器需要该路径，您可能需要在基础 URL 后追加 /v1。例如：spring.ai.openai.chat.base-url=http://localhost:12434/engines/v1，而不是 localhost:12434/engines。

    在使用 GPT-5 系列模型（如 gpt-5、gpt-5-mini 和 gpt-5-nano）时，不支持 temperature 参数。 这些模型专为推理任务优化，不使用温度参数。 若指定了温度值，将导致错误。 相比之下，对话类模型（如 gpt-5-chat）则支持 temperature 参数。
    您可以为 ChatModel 和 EmbeddingModel 实现覆盖通用的 spring.ai.openai.base-url 和 spring.ai.openai.api-key。 如果设置了 spring.ai.openai.chat.base-url 和 spring.ai.openai.chat.api-key 属性，它们将优先于通用属性。 如果您希望为不同的模型使用不同的 OpenAI 账户以及不同的模型端点，这将非常有用。
    所有以 spring.ai.openai.chat 开头的属性都可以通过向 Prompt 调用添加特定于请求的运行时选项在运行时进行覆盖。

    令牌限制参数：模型特定用法

    OpenAI 提供两个互斥的参数用于控制令牌生成限制：

    参数 使用场景 兼容型号

    maxTokens

    非推理模型

    gpt-4o, gpt-4o-mini, gpt-4-turbo, gpt-3.5-turbo

    maxCompletionTokens

    推理模型

    o1、o1-mini、o1-preview、o3 和 o4-mini 系列
    这些参数是互斥的。同时设置这两个参数会导致 OpenAI 返回 API 错误。

    使用示例

    对于非推理模型（gpt-4o、gpt-3.5-turbo）：

    ChatResponse response = chatModel.call(
    new Prompt(
        "Explain quantum computing in simple terms.",
        OpenAiChatOptions.builder()
            .model("gpt-4o")
            .maxTokens(150)  // Use maxTokens for non-reasoning models
        .build()
    ));

    针对推理模型（o1、o3 系列）：

    ChatResponse response = chatModel.call(
    new Prompt(
        "Solve this complex math problem step by step: ...",
        OpenAiChatOptions.builder()
            .model("o1-preview")
            .maxCompletionTokens(1000)  // Use maxCompletionTokens for reasoning models
        .build()
    ));

    构建器模式验证： OpenAI 的 ChatOptions 构建器会自动强制执行互斥性，采用“最后设置者胜”的策略：

    // This will automatically clear maxTokens and use maxCompletionTokens
OpenAiChatOptions options = OpenAiChatOptions.builder()
    .maxTokens(100)           // Set first
    .maxCompletionTokens(200) // This clears maxTokens and logs a warning
    .build();

// Result: maxTokens = null, maxCompletionTokens = 200

    运行时选项

    `OpenAiChatOptions.java` 类提供了模型配置，例如要使用的模型、温度、频率惩罚等。

    启动时，可以通过 `OpenAiChatModel(api, options)` 构造函数或 `spring.ai.openai.chat.*` 属性来配置默认选项。

    在运行时，您可以通过向 `Prompt` 调用添加新的、特定于请求的选项来覆盖默认选项。 例如，若要为特定请求覆盖默认的模型和温度：

    ChatResponse response = chatModel.call(
    new Prompt(
        "Generate the names of 5 famous pirates.",
        OpenAiChatOptions.builder()
            .model("gpt-4o")
            .temperature(0.4)
        .build()
    ));
    除了针对特定模型的OpenAiChatOptions之外，您还可以使用可移植的ChatOptions实例，该实例可通过ChatOptions#builder()创建。

    函数调用

    您可以使用 `OpenAiChatModel` 注册自定义 Java 函数，并让 OpenAI 模型智能地选择输出一个包含调用一个或多个已注册函数的参数的 JSON 对象。 这是一种将大语言模型能力与外部工具和 API 连接起来的强大技术。 有关工具调用的更多信息，请阅读 工具调用。

    OpenAiChatModel 不会在内部执行工具调用。 必须使用两种支持的方法之一在外部处理工具执行：

    • 使用 ToolCallingAdvisor 的 ChatClient——这是大多数用例的推荐方法。当存在工具时，ToolCallingAdvisor 会自动注册并透明地管理工具调用循环。

    • 用户控制的工具执行 — 当您需要对循环进行完全控制时（例如，在将工具调用与直接访问 ChatModel 相结合的情况下），请直接使用 DefaultToolCallingManager。

    通过 ChatClient 进行工具调用（推荐）

    使用 ChatClient 执行同步和流式工具调用。 当存在工具时，ToolCallingAdvisor 会自动注册，因此无需显式配置顾问。

    ToolCallback weatherCallback = FunctionToolCallback.builder("getCurrentWeather", new WeatherService())
    .description("Get the weather in location")
    .inputType(WeatherService.Request.class)
    .build();

// Synchronous
String response = ChatClient.create(chatModel)
    .prompt()
    .user("What's the weather in Paris, Tokyo, and New York?")
    .tools(weatherCallback)
    .call()
    .content();

// Streaming
Flux<String> stream = ChatClient.create(chatModel)
    .prompt()
    .user("What's the weather in Paris, Tokyo, and New York?")
    .tools(weatherCallback)
    .stream()
    .content();

    用户控制的工具执行

    当您需要直接访问ChatModel API 并希望完全控制工具调用循环时，请使用此模式。 直接调用ChatModel而无需使用ToolCallingAdvisor；自行检查工具调用情况，并使用ToolCallingManager驱动循环。

    ToolCallingManager toolCallingManager = ToolCallingManager.builder().build();

OpenAiChatOptions options = OpenAiChatOptions.builder()
    .toolCallbacks(ToolCallbacks.from(new WeatherService()))
    .build();

Prompt prompt = new Prompt("What's the weather in Paris, Tokyo, and New York?", options);
ChatResponse response = chatModel.call(prompt);

while (response.hasToolCalls()) {
    ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, response);
    prompt = new Prompt(result.conversationHistory(), options);
    response = chatModel.call(prompt);
}

    对于流式传输，请使用 `MessageAggregator`》聚合每个流式响应，以跨块检测工具调用：

    AtomicReference<ChatResponse> aggregatedRef = new AtomicReference<>();
new MessageAggregator()
    .aggregate(chatModel.stream(prompt), aggregatedRef::set)
    .collectList().block();

while (aggregatedRef.get().hasToolCalls()) {
    ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, aggregatedRef.get());
    prompt = new Prompt(result.conversationHistory(), options);
    aggregatedRef.set(null);
    new MessageAggregator()
        .aggregate(chatModel.stream(prompt), aggregatedRef::set)
        .collectList().block();
}

String content = aggregatedRef.get().getResult().getOutput().getText();

    Multimodal

    多模态是指模型同时理解和处理来自多种来源信息的能力，包括文本、图像、音频及其他数据格式。 OpenAI 支持文本、视觉和音频输入模态。

    结构化输出

    OpenAI 提供自定义的结构化输出API，确保您的模型生成的响应严格符合您提供的JSON Schema。 除了现有的 Spring AI 模型无关的结构化输出转换器外，这些 API 还提供了更高级的控制能力和更高的精度。

    目前，OpenAI 支持JSON Schema 语言子集格式。

    Configuration

    Spring AI 允许您通过程序化方式使用 `OpenAiChatOptions` 构建器，或通过应用程序属性来配置响应格式。

    使用聊天选项构建器

    您可以使用如下所示的 OpenAiChatOptions 构建器以编程方式设置响应格式：

        {
            "type": "object",
            "properties": {
                "steps": {
                    "type": "array",
                    "items": {
                        "type": "object",
                        "properties": {
                            "explanation": { "type": "string" },
                            "output": { "type": "string" }
                        },
                        "required": ["explanation", "output"],
                        "additionalProperties": false

                },

            "additionalProperties": false

Prompt prompt = new Prompt("how can I solve 8x + 7 = -23",
        OpenAiChatOptions.builder()

ChatResponse response = this.openAiChatModel.call(this.prompt);
    遵循 OpenAI JSON Schema 语言子集格式。

    与 BeanOutputConverter 工具集成

    您可以利用现有的BeanOutputConverter工具，从领域对象自动生成 JSON Schema，并将结构化响应转换为特定领域的实例：

    • Kotlin

    record MathReasoning(

	val steps: Steps,

    示例控制器

    创建一个新的 Spring Boot 项目，并在您的 pom（或 gradle）依赖中添加spring-ai-starter-model-openai。

    在 `src/main/resources` 目录下添加一个 `application.properties` 文件以启用并配置 OpenAI 聊天模型：

    spring.ai.openai.api-key=YOUR_API_KEY
spring.ai.openai.chat.model=gpt-4o
spring.ai.openai.chat.temperature=0.7
    将 api-key 替换为您的 OpenAI 凭据。

    这将创建一个 `OpenAiChatModel` 实现，您可以将其注入到类中。以下是一个使用聊天模型进行文本生成的简单 `@RestController` 类的示例。

    @RestController
public class ChatController {

    private final OpenAiChatModel chatModel;

    @Autowired
    public ChatController(OpenAiChatModel chatModel) {
        this.chatModel = chatModel;
    }

    @GetMapping("/ai/generate")
    public Map<String,String> generate(@RequestParam(value = "message", defaultValue = "Tell me a joke") String message) {
        return Map.of("generation", this.chatModel.call(message));
    }

    @GetMapping("/ai/generateStream")
	public Flux<ChatResponse> generateStream(@RequestParam(value = "message", defaultValue = "Tell me a joke") String message) {
        Prompt prompt = new Prompt(new UserMessage(message));
        return this.chatModel.stream(prompt);
    }
}

    <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-openai</artifactId>
</dependency>

    或者将其添加到您的 Gradle `build.gradle` 构建文件中。

    dependencies {

    请参考依赖管理部分，将 Spring AI BOM 添加到您的构建文件中。

    var chatModel = OpenAiChatModel.builder()

    API 密钥管理

    Observability

    Spring AI 会为每次 OpenAI 调用在两个层面发出 Micrometer 观测：

    • Chat 模型层。 每个对 OpenAiChatModel.call(…​) 或 .stream(…​) 的调用都会被一个 gen_ai.client.operation 观测所包裹，该观测包含请求参数、响应元数据以及 token 使用情况。有关完整的标签和指标集，请参阅可观测性参考。

    • HTTP 层。okhttp.requests 观察对象封装了针对 OpenAI API 的每一次 HTTP 请求，包含 HTTP 方法、URI、状态码和异常标签。每个请求还会在传输过程中传播 traceparent 头，以便下游服务（如 AI 网关、OpenAI 兼容推理服务器或代理）能够进行追踪。

    在包含 `spring-boot-starter-actuator` 和追踪桥接器（`micrometer-tracing-bridge-otel` 或 `micrometer-tracing-bridge-brave`）的 Spring Boot 应用中，这两层会自动配置——无需显式启用。 对于非 Boot 应用，请将 `ObservationRegistry` 传递给 `OpenAiChatModel.builder()`：

    OpenAiChatModel chatModel = OpenAiChatModel.builder()
    .options(...)
    .observationRegistry(observationRegistry)
    .build();

    连接池指标（需主动启用）

    Spring AI 还可以将 OkHttp 连接池指标（okhttp.pool.connection.count，其中 state=active|idle 和 client.kind=sync|async）绑定到应用程序的 MeterRegistry。 这些属于次要遥测数据——可用于容量调优，但并非追踪或请求级延迟所必需——因此默认处于禁用状态。

    要在 Spring Boot 应用程序中启用它们：

    spring.ai.openai.chat.connection-pool-metrics-enabled=true

    对于非 Boot 应用，直接将 `MeterRegistry` 传递给构建器；只要提供了注册表，仪表就会自动绑定：

    OpenAiChatModel chatModel = OpenAiChatModel.builder()
    .options(...)
    .observationRegistry(observationRegistry)
    .meterRegistry(meterRegistry)
    .build();

    HTTP 调度器执行器（高级）

    默认情况下，Spring AI 管理 OkHttp 分发器的执行器——这是一个无界平台线程池，复现了 SDK 的默认行为。 对于具有高 HTTP 并发的工作负载，或为了利用 Java 21+ 中的虚拟线程，您可以提供自己的 ExecutorService：

    OpenAiChatModel chatModel = OpenAiChatModel.builder()
    .options(...)
    .dispatcherExecutor(Executors.newVirtualThreadPerTaskExecutor())
    .build();

    同一个执行器同时支持同步和异步（流式）客户端。 当您提供自己的执行器时，您负责其生命周期管理——Spring AI 永远不会调用其 shutdown() 方法。 若未指定，则会自动创建并清理内部执行器。

    流式传输的 HTTP 观测结果未作为聊天模型观测结果的子项

    对于同步调用，`okhttp.requests` 跨度正确嵌套在 `gen_ai.client.operation` 跨度之下——完整的追踪树按预期形成。

    对于流式调用，`okhttp.requests` 跨度会触发并在注册表中记录，计时器记录在 `MeterRegistry` 中，且 `traceparent` 仍会在出站请求中传播——但该跨度不会嵌套在 chat-model 跨度之下。 这是因为 OpenAI SDK 的异步流式实现会在调用 Spring AI 的 HTTP 客户端之前跳转到 `ForkJoinPool.commonPool()`，从而在该边界处丢失了调用线程的观察上下文。 Spring AI 无法从其 HTTP 客户端包装器内部恢复该上下文。

    如果您需要在追踪 UI 中将流式 HTTP 跨度与其父级 chat-model 跨度进行关联，请筛选跨度名称为 okhttp.requests 且主机为 api.openai.com 的记录，然后通过跟踪 ID 或时间戳范围将其与对应的 gen_ai.client.operation 跨度连接。 OpenAI Java SDK 正在上游开发流式的内置父级关联功能。

    自定义 HTTP 客户端

    Spring AI 在底层使用官方的 openai-java SDK，并通过由 SpringAiOpenAiHttpClient.Builder 构建的自定义 OkHttp 客户端配置其 HTTP 传输层。 您可以通过暴露一个或多个 OpenAiHttpClientBuilderCustomizer Bean 来拦截该 Builder，在底层 OkHttpClient 创建之前进行定制。 每个定制器都会接收到 OpenAI 所有模型（包括聊天、嵌入、图像、音频和审核）所使用的相同 Builder，因此定制效果将统一应用。

    @FunctionalInterface
public interface OpenAiHttpClientBuilderCustomizer {
    void customize(SpringAiOpenAiHttpClient.Builder builder);
}

    典型应用场景包括：

    • 注册 OkHttp Interceptor 实例（用于身份验证、传播请求头、自定义日志记录）；

    • 交换调度器 `ExecutorService`（例如，将异步 I/O 路由到虚拟线程）；

    • 配置代理、SSL、主机名验证或构建器暴露的连接池大小。

    当存在多个自定义器时，它们将在 Spring AI 自身的默认配置之后，按照 `@Order` / `Ordered` 的顺序应用，因此用户代码具有最高优先级。

    在通过 `OpenAi*Model.Builder` 手动构建模型时，也可以使用相同的钩子：

    var chatModel = OpenAiChatModel.builder()
    .options(OpenAiChatOptions.builder().model("gpt-4o").build())
    .httpClientBuilderCustomizer(myCustomizer)
    .build();

    使用额外参数与 OpenAI 兼容服务器

    像 vLLM、Ollama 等兼容 OpenAI 的推理服务器，通常支持超出 OpenAI 标准 API 定义范围的额外参数。例如，这些服务器可能接受诸如 top_k、repetition_penalty 或其他采样控制参数，而官方 OpenAI API 并不识别这些参数。

    `extraBody` 选项允许您向这些服务器传递任意参数。 在 `extraBody` 中提供的任何键值对都会包含在 JSON 请求的顶层，使您可以在使用 Spring AI 的 OpenAI 客户端的同时利用特定于服务器的功能。

    `extraBody` 参数专为与 OpenAI 兼容的服务器使用而设计，不适用于官方 OpenAI API。 官方 OpenAI API 会执行严格的验证，若遇到未识别的字段，将返回 HTTP 400 错误（`"Unknown parameter: 'extra_body'"`）。

    如果您正在与官方 OpenAI API 通信，则绝不应填充 extraBody 参数。

    此外，请注意在序列化过程中，`extraBody` Map 会被有意扁平化到 JSON 请求的顶层。因此，设置 `extraBody(Map.of("custom_flag", true))` 会导致 `"custom_flag": true` 出现在 JSON 负载的根节点处，这与官方 SDK 的行为一致。

    使用属性进行配置

    您可以使用 Spring Boot 属性配置额外的参数。 `spring.ai.openai.chat.extra-body` 下的每个属性都会成为请求中的顶层参数：

    spring.ai.openai.base-url=http://localhost:8000
spring.ai.openai.chat.model=meta-llama/Llama-3-8B-Instruct
spring.ai.openai.chat.temperature=0.7
spring.ai.openai.chat.extra-body.top_k=50
spring.ai.openai.chat.extra-body.repetition_penalty=1.1

    此配置将生成如下 JSON 请求：

    {
  "model": "meta-llama/Llama-3-8B-Instruct",
  "temperature": 0.7,
  "top_k": 50,
  "repetition_penalty": 1.1,
  "messages": [...]
}

    使用构建器进行运行时配置

    此外，您还可以通过选项构建器在运行时指定额外参数：

    ChatResponse response = chatModel.call(
    new Prompt(
        "Tell me a creative story",
        OpenAiChatOptions.builder()
            .model("meta-llama/Llama-3-8B-Instruct")
            .temperature(0.7)
            .extraBody(Map.of(
                "top_k", 50,
                "repetition_penalty", 1.1,
                "frequency_penalty", 0.5
            ))
            .build()
    ));

    示例：vLLM 服务器

    使用 vLLM 运行 Llama 模型时，您可能希望使用针对 vLLM 特定的采样参数：

    spring.ai.openai.base-url=http://localhost:8000
spring.ai.openai.chat.model=meta-llama/Llama-3-70B-Instruct
spring.ai.openai.chat.extra-body.top_k=40
spring.ai.openai.chat.extra-body.top_p=0.95
spring.ai.openai.chat.extra-body.repetition_penalty=1.05
spring.ai.openai.chat.extra-body.min_p=0.05

    有关支持的采样参数完整列表，请参阅vLLM 文档。

    示例：Ollama 服务器

    通过 OpenAI 兼容端点使用 Ollama 时，您可以传递特定于 Ollama 的参数：

    OpenAiChatOptions options = OpenAiChatOptions.builder()
    .model("llama3.2")
    .extraBody(Map.of(
        "num_predict", 100,
        "top_k", 40,
        "repeat_penalty", 1.1
    ))
    .build();

ChatResponse response = chatModel.call(new Prompt("Generate text", options));

    有关可用参数，请参阅Ollama API 文档。

    `extraBody` 参数接受任何 `Map`，允许您传递目标服务器支持的任何参数。 Spring AI 不会验证这些参数——它们会直接传递给服务器。 这种设计为与各种 OpenAI 兼容的实现进行交互提供了最大的灵活性。

    推理模型生成的推理内容

    一些支持推理模型（如 DeepSeek R1、带有推理解析器的 vLLM）的 OpenAI 兼容服务器，会通过其 API 响应中的 `reasoning_content` 字段暴露模型的内部思维链。该字段包含了模型得出最终答案所采用的逐步推理过程。

    Spring AI 将该字段从 JSON 响应映射到 AssistantMessage 元数据中的reasoningContent键。

    关于 reasoning_content 可用性的一个重要区别：

    • 兼容 OpenAI 的服务器（如 DeepSeek、vLLM）：在聊天补全 API 响应中暴露 reasoning_content ✅

    • 官方 OpenAI 模型（GPT-5、o1、o3）：请勿在聊天补全 API 响应中暴露推理文本 ❌

    官方 OpenAI 推理模型在使用 Chat Completions API 时会隐藏思维链内容，仅在使用统计信息中暴露 reasoning_tokens 计数。 要从官方 OpenAI 模型获取实际的推理文本，必须使用 OpenAI 的 Responses API（这是一个当前该客户端不支持的独立端点）。

    回退行为：当服务器未提供reasoning_content（例如官方 OpenAI 聊天补全服务）时，reasoningContent元数据字段将是一个空字符串。

    访问推理内容

    在使用兼容的服务器时，您可以从响应元数据中访问推理内容。

    直接使用 ChatModel：

    // Configure to use DeepSeek R1 or vLLM with a reasoning model
ChatResponse response = chatModel.call(
    new Prompt("Which number is larger: 9.11 or 9.8?")
);

// Get the assistant message
AssistantMessage message = response.getResult().getOutput();

// Access the reasoning content from metadata
String reasoning = message.getMetadata().get("reasoningContent");
if (reasoning != null && !reasoning.isEmpty()) {
    System.out.println("Model's reasoning process:");
    System.out.println(reasoning);
}

// The final answer is in the regular content
System.out.println("\nFinal answer:");
System.out.println(message.getContent());

    使用 ChatClient：

    ChatClient chatClient = ChatClient.create(chatModel);

String result = chatClient.prompt()
    .user("Which number is larger: 9.11 or 9.8?")
    .call()
    .chatResponse()
    .getResult()
    .getOutput()
    .getContent();

// To access reasoning content with ChatClient, retrieve the full response
ChatResponse response = chatClient.prompt()
    .user("Which number is larger: 9.11 or 9.8?")
    .call()
    .chatResponse();

AssistantMessage message = response.getResult().getOutput();
String reasoning = message.getMetadata().get("reasoningContent");

    流式推理内容

    在使用流式响应时，推理内容会像普通消息内容一样在各个数据块中累积：

    Flux<ChatResponse> responseFlux = chatModel.stream(
    new Prompt("Solve this logic puzzle...")
);

StringBuilder reasoning = new StringBuilder();
StringBuilder answer = new StringBuilder();

responseFlux.subscribe(chunk -> {
    AssistantMessage message = chunk.getResult().getOutput();

    // Accumulate reasoning if present
    String reasoningChunk = message.getMetadata().get("reasoningContent");
    if (reasoningChunk != null) {
        reasoning.append(reasoningChunk);
    }

    // Accumulate the final answer
    if (message.getContent() != null) {
        answer.append(message.getContent());
    }
});

    示例：DeepSeek R1

    DeepSeek R1 是一个推理模型，能够展示其内部推理过程：

    spring.ai.openai.api-key=${DEEPSEEK_API_KEY}
spring.ai.openai.base-url=https://api.deepseek.com
spring.ai.openai.chat.model=deepseek-reasoner

    当您向 DeepSeek R1 发送请求时，响应将同时包含推理内容（即模型的思考过程）和最终答案。

    有关推理模型的详细信息，请参阅DeepSeek API 文档。

    示例：使用推理解析器的 vLLM

    当配置了推理解析器时，vLLM 支持推理模型：

    vllm serve deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B \
    --enable-reasoning \
    --reasoning-parser deepseek_r1
    spring.ai.openai.base-url=http://localhost:8000

    有关支持的推理模型和解析器，请参阅vLLM 推理输出文档。

    `reasoning_content` 的可用性完全取决于您所使用的推理服务器。 并非所有兼容 OpenAI 的服务器都会暴露推理内容，即使使用的是具备推理能力的模型。 请务必查阅服务器的 API 文档，以了解响应中可用的字段。

    OpenAI 兼容提供者的工具调用附加属性

    某些兼容 OpenAI 的提供商会在其响应中的工具调用对象中附加额外字段。一个常见的例子是 Google Gemini 的兼容 OpenAI 端点，它返回一个用于多轮工具调用的必需字段 thought_signature：

    {
  "tool_calls": [
    {
      "id": "call_1",
      "type": "function",
      "function": { "name": "get_weather", "arguments": "{\"location\":\"Seoul\"}" },
      "extra_content": { "google": { "thought_signature": "..." } }
    }
  ]
}

    若后续请求中缺少这些特定于提供者的字段，某些模型将拒绝工具调用历史。

    Spring AI 会自动捕获工具调用对象中存在的任何额外字段，并在助手消息被包含在后续请求时原样重放这些字段。 无需进行任何配置——该行为对阻塞式和流式处理流程均透明可见。

    此规则仅适用于工具调用对象本身的额外字段。嵌套在 `function` 对象内部的额外字段不会被保留。
