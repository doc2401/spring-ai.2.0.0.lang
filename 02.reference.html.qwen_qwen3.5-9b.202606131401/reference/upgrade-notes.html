    升级说明

    升级至 2.0.0

    本节涵盖了从 Spring AI 1.1.x 升级到 2.0.0 时的所有破坏性变更和迁移步骤。

    Advisors

    spring-ai-advisors-vector-store 已重命名为 spring-ai-vector-store-advisor

    spring-ai-advisors-vector-store 模块已重命名为 spring-ai-vector-store-advisor，以更符合其他 Spring AI 模块的命名规范。

    ToolSearchToolCallingAdvisor 已移至 spring-ai-tool-search-advisor

    ToolSearchToolCallingAdvisor 类已移至专用模块和包：

    • 构件：spring-ai-tool-search-advisor（此前包含在spring-ai-tool-search-tool中）

    • Package: org.springframework.ai.chat.client.advisor.toolsearch (previously org.springframework.ai.tool.toolsearch.advisor)

    请相应地更新您的依赖项和导入语句：

    <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-tool-search-advisor</artifactId>
</dependency>

    新增：ToolSearchToolCallingAdvisor 自动配置与启动器

    现已提供 Spring Boot 自动配置（spring-ai-autoconfigure-tool-search-advisor）及对应的启动器（spring-ai-starter-tool-search-advisor）。启用后，ToolSearchToolCallingAdvisor 将替换自动配置的 ChatClient 中的默认 ToolCallingAdvisor，从而限制每次调用发送给 LLM 的工具定义数量，仅包含最相关的工具（通过关键词或语义搜索筛选）。

    通过添加启动器并设置该属性来启用：

    <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-tool-search-advisor</artifactId>
</dependency>
    spring.ai.chat.client.tool-search-advisor.enabled=true

# Choose the index type: regex (default), lucene, or vector
spring.ai.chat.client.tool-search-advisor.tool-index-type=regex

    regex 索引无需额外的依赖项。 lucene 索引需要在类路径中包含 org.apache.lucene:lucene-core。 vector 索引需要一个 VectorStore Bean（类路径中需包含 spring-ai-vector-store）。

    变更：Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER 的默认值

    Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER 已从 Ordered.HIGHEST_PRECEDENCE + 1000 更改为 Ordered.HIGHEST_PRECEDENCE + 200，将内存顾问的默认顺序置于 ToolCallingAdvisor（HIGHEST_PRECEDENCE + 300）之外。

    ToolCallingAdvisor 现在默认在工具调用迭代过程中内部管理对话历史。记忆顾问仅存储最终的用户/助手交互，从不将工具调用消息写入 ChatMemoryRepository。这是正确的默认行为，因为大多数仓库实现并不支持这些消息类型。

    如果您需要在循环内部使用内存（例如配合InMemoryChatMemoryRepository），请明确将顾问顺序设置为高于ToolCallingAdvisor.DEFAULT_ORDER，并调用.disableInternalConversationHistory()：

    var toolCallingAdvisor = ToolCallingAdvisor.builder()
    .disableInternalConversationHistory()
    .build();
var chatMemoryAdvisor = MessageChatMemoryAdvisor.builder(chatMemory)
    .advisorOrder(Ordered.HIGHEST_PRECEDENCE + 400)
    .build();
    spring-ai-session 社区项目提供了一个支持会话记忆的内存实现，完全支持工具调用消息，并且可以安全地在任何后端中的工具调用循环中使用。它计划将在 Spring AI 2.1 中取代 ChatMemory。有关详细信息，请参阅 spring-ai-session 文档。

    工具调用

    Removed: internalToolExecutionEnabled from ToolCallingChatOptions

    `ToolCallingChatOptions` 类中的所有 provider 特定的 `ChatOptions` 类（例如 `OpenAiChatOptions`、`AnthropicChatOptions`）中的 `internalToolExecutionEnabled` 选项已被移除。相应的 Spring Boot 配置属性 `spring.ai.<provider>.chat.internal-tool-execution-enabled` 也已被移除。

    Impact

    将 `.internalToolExecutionEnabled(false)` 设置为以启用用户控制的工具执行，该代码将不再编译。 将 `.internalToolExecutionEnabled(true)`（显式启用内部循环）的代码也将不再编译，且其原本隐含的行为已不复存在——所有 `ChatModel` 实现中均已移除了每模型内部工具执行功能。

    Migration

    移除所有对 `.internalToolExecutionEnabled(…​)` 的调用。推荐的方法如下：

    • ToolCallingAdvisor 通过 ChatClient（推荐）——当存在工具时自动注册；无需设置标志。

    • 通过 ChatModel 直接实现用户控制的循环——只需直接调用 ChatModel，无需使用 ToolCallingAdvisor。工具调用不会自动执行；请自行检查 chatResponse.hasToolCalls()，并使用 ToolCallingManager 驱动循环。

    // Before
ChatOptions options = ToolCallingChatOptions.builder()
    .toolCallbacks(ToolCallbacks.from(new MyTools()))
    .internalToolExecutionEnabled(false)   // <-- remove this line
    .build();

// After
ChatOptions options = ToolCallingChatOptions.builder()
    .toolCallbacks(ToolCallbacks.from(new MyTools()))
    .build();

    Removed: ToolExecutionEligibilityPredicate and DefaultToolExecutionEligibilityPredicate

    ToolExecutionEligibilityPredicate（自 2.0.0 版本起已弃用）及其默认实现 DefaultToolExecutionEligibilityPredicate 已被移除。这些接口结合了基于选项的策略检查（internalToolExecutionEnabled）与响应检查（hasToolCalls()）。由于基于选项的标志已不再存在，因此在 ChatModel 级别没有相应的替代方案。

    Migration

    如果您实现了ToolExecutionEligibilityPredicate来自定义工具执行的触发时机，请迁移至使用ToolExecutionEligibilityChecker（见下文），并将其提供给ToolCallingAdvisor。

    New: ToolExecutionEligibilityChecker in ToolCallingAdvisor

    ToolExecutionEligibilityChecker（类型为Function<ChatResponse, Boolean>）现在可以设置于ToolCallingAdvisor.Builder，以自定义工具调用循环的迭代时机。默认值为chatResponse → chatResponse != null && chatResponse.hasToolCalls()。

    这是用于特定提供者停止原因逻辑的扩展点（例如，除了检查工具调用是否存在外，还需检查结束原因）：

    ToolCallingAdvisor advisor = ToolCallingAdvisor.builder()
    .toolExecutionEligibilityChecker(response ->
        response != null && response.hasToolCalls()
            && !"stop".equals(response.getResult().getMetadata().getFinishReason()))
    .build();

    Spring Boot 用户可以提供一个 `ToolExecutionEligibilityChecker` Bean；它将被自动配置的 `ToolCallingAdvisor.Builder` 自动拾取：

    @Bean
ToolExecutionEligibilityChecker myChecker() {
    return response -> response != null && response.hasToolCalls();
}

    New: spring.ai.chat.client.tool-calling.enabled Property

    新增的 `spring.ai.chat.client.tool-calling.enabled` 属性（默认值为 `true`）用于控制是否由自动配置的 `ChatClient` 自动注册 `ToolCallingAdvisor`。将其设置为 `false` 可禁用所有调用的自动工具执行——工具仍作为定义发送给 AI 模型，但不会自动执行工具调用响应。

    spring.ai.chat.client.tool-calling.enabled=false

    这是在每个单独调用中使用 `AdvisorParams.toolCallingAdvisorAutoRegister(false)` 的全局替代方案。

    已移除：顾问构建器和自动配置中的streamToolCallResponses

    `streamToolCallResponses` 选项已从 `ToolCallingAdvisor.Builder`、`ToolCallAdvisor.Builder` 和 `ToolSearchToolCallingAdvisor.Builder` 中移除，同时也从其对应的 Spring Boot 自动配置属性中移除：

    • spring.ai.chat.client.tool-calling.stream-tool-call-responses

    • spring.ai.chat.client.tool-search-advisor.stream-tool-call-responses

    Why

    当 `streamToolCallResponses=true` 时，中间的工具调用请求片段会被流式传输到下游，但配对的 `ToolResponseMessage`（发送回 LLM 的消息）则不会。任何记录这些片段的下游内存顾问都会收到缺少相应工具响应的工具调用请求，从而导致对话历史损坏。由于修复此设计缺陷需要对 `ChatClientResponse` 引入破坏性变更，因此该选项已被完全移除。

    Impact

    • 任何在顾问构建器上调用 `.streamToolCallResponses(true)` 或 `.streamToolCallResponses(false)` 的代码都将无法编译。

    • 任何已移除属性的application.properties或application.yml条目均会被静默忽略。

    Migration

    从您的构建链中移除所有对 `.streamToolCallResponses(…​)` 的调用：

    // Before
var advisor = ToolCallingAdvisor.builder()
    .streamToolCallResponses(true)   // <-- remove this line
    .build();

// After
var advisor = ToolCallingAdvisor.builder().build();

    为了获得工具调用循环（即 `streamToolCallResponses=true` 旨在解决的使用场景）中每一次迭代的可见性，请取消自动注册的顾问，并通过 `AdvisorParams.toolCallingAdvisorAutoRegister(false)` 手动驱动该循环：

    ToolCallingManager toolCallingManager = ToolCallingManager.builder().build();
ToolCallback[] tools = ToolCallbacks.from(new WeatherTools());
ChatOptions chatOptions = ToolCallingChatOptions.builder()
    .toolCallbacks(tools)
    .build();

String question = "What is the weather in Amsterdam and Paris?";
Prompt prompt = new Prompt(List.of(new UserMessage(question)), chatOptions);

ChatClientResponse response = chatClient.prompt()
    .user(question)
    .options(chatOptions)
    .advisors(AdvisorParams.toolCallingAdvisorAutoRegister(false))
    .call()
    .chatClientResponse();

while (response.chatResponse() != null && response.chatResponse().hasToolCalls()) {
    // inspect or forward the tool-call chunk here before executing
    ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, response.chatResponse());
    prompt = new Prompt(result.conversationHistory(), chatOptions);
    response = chatClient.prompt()
        .messages(result.conversationHistory())
        .options(chatOptions)
        .advisors(AdvisorParams.toolCallingAdvisorAutoRegister(false))
        .call()
        .chatClientResponse();
}
// forward or process the final answer here

    有关包含流式传输路径的完整示例，请参阅用户控制的工具执行——配合 ChatClient 使用。

    JDBC 聊天记忆 `sequence_id` 列

    JdbcChatMemoryRepository 架构新增了一个 sequence_id BIGINT 列，用于确定对话中消息的排序。此前，排序依赖于 timestamp 列，但由于不同数据库的 TIMESTAMP 精度存在差异——在 MySQL 和 MariaDB 中默认精度为秒级，因此同一秒内保存的消息会以非确定性顺序返回。专用的整数序列在所有支持的数据库中均保持一致的排序。

    保留 `timestamp` 列。该列现在存储消息的创建时间，并通过键 `JdbcChatMemoryRepository.CONVERSATION_TS`（类型为 `java.time.Instant`）在消息元数据中暴露，以便应用程序能够显示消息的创建时间。该时间戳在保存过程中得以保留：重新保存对话会保持每条现有消息的原始创建时间不变。

    Impact

    • `SPRING_AI_CHAT_MEMORY` 表新增 `sequence_id` 列（类型为 `BIGINT`，在 Oracle 上为 `NUMBER(19)`，在 SQLite 上为 `INTEGER`）以及 `SPRING_AI_CHAT_MEMORY_CONVERSATION_ID_SEQUENCE_ID_IDX` 索引。`timestamp` 列及其索引保持不变。

    • Spring AI 1.x 创建的现有表需要添加新列才能正常工作，因为消息现在按 `sequence_id` 排序。

    • 从仓库读取的消息现在会在元数据中包含其创建时间戳。由于元数据的差异，通过代码构建的与否则完全相同的消息不再相等（Message.equals）。因此，按值比较消息的代码，或依赖消息身份用于集合或映射中的代码，都应对此做出相应处理。

    Migration

    该变更是累加的：添加新列，并从现有的每会话顺序中回填数据。不会丢失任何数据，且 `timestamp` 列保持不变。对于 PostgreSQL：

    ALTER TABLE SPRING_AI_CHAT_MEMORY ADD COLUMN sequence_id BIGINT;

WITH ordered AS (
    SELECT ctid, ROW_NUMBER() OVER (PARTITION BY conversation_id ORDER BY "timestamp") - 1 AS seq
    FROM SPRING_AI_CHAT_MEMORY
)
UPDATE SPRING_AI_CHAT_MEMORY t
SET sequence_id = o.seq
FROM ordered o
WHERE t.ctid = o.ctid;

ALTER TABLE SPRING_AI_CHAT_MEMORY ALTER COLUMN sequence_id SET NOT NULL;

CREATE INDEX SPRING_AI_CHAT_MEMORY_CONVERSATION_ID_SEQUENCE_ID_IDX
ON SPRING_AI_CHAT_MEMORY(conversation_id, sequence_id);

    根据您的数据库调整标识符引号和行身份表达式（即上文中的ctid）。ROW_NUMBER() OVER (PARTITION BY conversation_id ORDER BY <timestamp>) 模式可在所有支持的引擎上重现现有的每会话顺序。或者，由于聊天记忆存储的是最近的对话上下文而非永久历史记录，您可以从更新的 schema-<platform>.sql 脚本中删除并重建该表。

    选项的不可变性与默认值

    选项的严格不可变性

    Options 类（如ChatOptions、EmbeddingOptions等）现已严格不可变。 Options 中的集合（如toolCallbacks、stopSequences、customHeaders）现在以不可修改的集合形式存储。 此外，现使用可空集合而非空集合，以更准确地表示值的缺失。

    Impact

    • `ChatOptions#copy()` 和 `*Options#fromOptions(*Options)` 方法已被移除，因为选项现在必须是严格不可变的。

    • 修改由选项获取器返回的集合将抛出UnsupportedOperationException。

    Migration

    要创建选项实例的修改副本，请使用 mutate() 方法，而不是 copy() 或 fromOptions()：

    // Before
OllamaChatOptions options = originalOptions.copy();
options.setFoo("...");

// After
OllamaChatOptions options = originalOptions.mutate()
        .foo("...")
        .build();

    默认值已移至选项构造函数

    选项的默认值（例如默认模型名称、温度等）已从 `Model` 实现类和 `*Properties` 配置类中移至选项构造函数本身。 `*Properties` 类中的默认配置属性已被移除，因为它们不再需要，且应与选项级别的默认值保持一致。

    Impact

    • ChatModel#getDefaultOptions() 已被弃用，建议使用 ChatModel#getOptions()。

    • 默认值不再在 `*Properties` 类中重复。

    Migration

    检索模型默认选项时，请使用getOptions()而非getDefaultOptions()：

    // Before
ChatOptions options = chatModel.getDefaultOptions();

// After
ChatOptions options = chatModel.getOptions();

    配置属性扁平化

    基于上述聊天配置变更，其他所有模型（包括嵌入、图像、音频、内容审核、OCR 等）的配置属性不再使用 `.options` 前缀。 例如，之前的 `spring.ai.openai.embedding.options.model` 现在已改为 `spring.ai.openai.embedding.model`。 为确保迁移过程更加顺畅，系统仍提供针对 `.options` 变体的废弃配置属性。

    Impact

    • `*Properties` 类中的 `getOptions()` 方法已弃用。

    • 嵌套在 `*Properties` 中的 `Options` 类已弃用。

    • `toOptions()` 方法已从嵌套的 `Options` 类移至根 `*Properties` 类。

    Migration

    更新您的 `application.properties` 或 `application.yml`，从属性键中移除 `.options` 部分。

    # Before
spring.ai.openai.embedding.options.model=text-embedding-3-small

# After
spring.ai.openai.embedding.model=text-embedding-3-small

    在 Java 代码中，直接使用根属性类访问选项或调用toOptions()：

    // Before
String model = properties.getOptions().getModel();
OpenAiEmbeddingOptions options = properties.getOptions().toOptions();

// After
String model = properties.getModel();
OpenAiEmbeddingOptions options = properties.toOptions();

    在选项构建器中将 N() 重命名为 n()

    各种 `*Options` 和配置属性类中的 `N()` 构建器方法已重命名为 `n()`，以符合 Java 命名约定。

    Impact

    • 任何在这些构建器上调用 `.N(value)` 的 Java 代码都将无法编译。

    Migration

    请更新您的代码，改为调用 `.n(value)`。

    // Before
OpenAiChatOptions.builder().N(1).build();

// After
OpenAiChatOptions.builder().n(1).build();

    Ollama

    Renamed: spring.ai.ollama.chat.think-option to spring.ai.ollama.chat.think

    spring.ai.ollama.chat.think-option 配置属性已重命名为 spring.ai.ollama.chat.think。

    相应地更新您的 `application.properties` 或 `application.yml`：

    # Before
spring.ai.ollama.chat.think-option=true

# After
spring.ai.ollama.chat.think=true

    Minimax 专属支持已被 Anthropic 支持取代

    Minimax 的专用支持已移除，建议改用由 Minimax 官方推荐的 Anthropic 支持。 请使用 Spring AI 的 Anthropic 支持，并将其配置为使用 https://api.minimax.io/anthropic 作为基础 URL，同时指定 MiniMax 模型。 不再支持嵌入功能。

    JSON 工具重构

    新增：JsonHelper 和更新后的 JacksonUtils

    在 `spring-ai-commons` 中引入了一个新的 `JsonHelper` 类，作为执行 JSON 序列化和反序列化的标准方式。该类可实例化并支持自定义的 `JsonMapper`，使得针对特定用例定制 JSON 行为变得轻而易举。此外，`JacksonUtils` 新增了一个静态方法 `getDefaultJsonMapper()`，用于返回一个共享且预配置的 `JsonMapper` 实例。

    JsonHelper 将此前分散在 JsonParser、ModelOptionsUtils 和 McpJsonParser 中的 JSON 操作进行了集中。默认构造函数使用来自 JacksonUtils.getDefaultJsonMapper() 的共享映射器。如果您需要不同的序列化设置，请注入自定义的 JsonMapper：

    // Default — uses the shared JsonMapper from JacksonUtils
JsonHelper jsonHelper = new JsonHelper();

// Custom — supply your own JsonMapper
JsonMapper myMapper = JsonMapper.builder()
    .addModule(new JavaTimeModule())
    .build();
JsonHelper customHelper = new JsonHelper(myMapper);

    Deprecated: JsonParser

    JsonParser（位于 org.springframework.ai.util.json）已标记为即将移除的弃用状态。所有方法现已委托给 JsonHelper。

    Impact

    调用JsonParser方法的代码将在编译时收到弃用警告。

    Migration
    Before After

    JsonParser.getJsonMapper()

    JacksonUtils.getDefaultJsonMapper()

    JsonParser.fromJson(json, MyType.class)

    jsonHelper.fromJson(json, MyType.class)

    JsonParser.fromJson(json, type)

    jsonHelper.fromJson(json, type)

    JsonParser.toJson(object)

    jsonHelper.toJson(object)

    JsonParser.toTypedObject(value, type)

    jsonHelper.convertToTypedObject(value, type)

    已移除：来自ModelOptionsUtils的JSON方法

    由于模型选项不再直接依赖 Jackson，ModelOptionsUtils 中的以下成员已被移除。

    移除的成员 替换项

    ModelOptionsUtils.JSON_MAPPER

    ChatClient 工具调用

    Automatic ToolCallingAdvisor Registration

    ChatClient 现在始终会在顾问链中自动注册一个 ToolCallingAdvisor（除非显式禁用），因此无论工具是静态配置还是由其他顾问在运行时注入，模型请求的工具调用都能得到自动处理。

    Impact

    现有代码如果显式添加了ToolCallingAdvisor，则该顾问会在链中出现两次——一次来自显式添加，另一次来自自动注册。

    Migration

    从链中移除显式的ToolCallingAdvisor，并让自动注册机制来处理它。如果您需要自定义配置，可以在构建ChatClient时提供一个预配置的ToolCallingAdvisor.Builder（请参阅自定义默认 ToolCallingAdvisor部分），或者禁用自动注册并手动注册该顾问：

    // Before — manual registration
chatClient.prompt("What's the weather?")
    .tools(weatherTool)
    .advisors(ToolCallingAdvisor.builder().build())
    .call().content();

// After — auto-registration handles it; no explicit advisor needed
chatClient.prompt("What's the weather?")
    .tools(weatherTool)
    .call().content();

// Or, to keep full control, disable auto-registration explicitly
chatClient.prompt("What's the weather?")
    .tools(weatherTool)
    .advisors(
        AdvisorParams.toolCallingAdvisorAutoRegister(false),
        ToolCallingAdvisor.builder().build()
    )
    .call().content();

    新增：ToolAdvisor 标记接口

    已添加一个名为 `ToolAdvisor` 的标记接口。`ToolCallingAdvisor` 实现了该接口。`DefaultChatClient` 会检查此标记，以决定是否自动注册一个 `ToolCallingAdvisor`——如果链中的任何 advisor 已经实现了 `ToolAdvisor`，则跳过自动注册。

    拥有工具调用生命周期的自定义顾问应实现ToolAdvisor，以防止自动添加重复的ToolCallingAdvisor。

    新增：MemoryAdvisor 标记接口

    已添加 `MemoryAdvisor` 标记接口。BaseChatMemoryAdvisor 现已继承该接口。DefaultChatClient 利用此标记来检测下游内存顾问，并在存在此类顾问时禁用 `ToolCallingAdvisor` 的内部对话历史。

    自定义内存顾问若未继承BaseChatMemoryAdvisor但需与工具调用自动注册逻辑集成，则应实现MemoryAdvisor接口。

    新增：用于自定义ToolCallingAdvisor配置的ChatClient.builder()重载方法

    新增了一个接受 `ToolCallingAdvisor.Builder<?>` 参数的五参数静态方法 `ChatClient.builder()`，以及与之匹配的 `DefaultChatClientBuilder` 构造函数，用于配置在自动注册期间使用的顾问：

    ChatClient chatClient = ChatClient
    .builder(chatModel, observationRegistry, null, null,
            ToolCallingAdvisor.builder().toolCallingManager(myToolCallingManager))
    .build();

    Spring Boot 用户应优先采用以下方案之一：

    • 将 `spring.ai.chat.client.tool-calling.advisor-order` 设置为控制顾问在链中的位置。

    • 声明一个 `ToolCallingAdvisor.Builder<?>` 类型的 Bean，以完全替换自动配置的构建器（该配置通过 `@ConditionalOnMissingBean` 被抑制）。

    已移除：ChatClient 上的 ToolSpec 消费者 API

    已移除 `tools(Consumer)` / `defaultTools(Consumer)` API 以及 `ChatClient.ToolSpec` 接口。现在，`tools(Object…)` / `defaultTools(Object…)` 方法直接接受 `ToolCallback`、`ToolCallbackProvider`、带有 `@Tool` 注解的 POJO 实例，以及上述任意类型的集合或数组。上下文通过专用的 `toolContext()` / `defaultToolContext()` 方法单独设置。

    .tools(t -> t.callbacks(myCallback).context("tenantId", "acme"))
    .call().content();

// After

    .tools(myCallback)
    .toolContext(Map.of("tenantId", "acme"))

    • 当多个工具对象产生具有重复名称的回调时。

    BeanOutputConverter JSON 模式生成

    `BeanOutputConverter` 现已将 JSON Schema 生成功能委托给 `JsonSchemaGenerator`，使结构化输出转换与工具调用中使用的 JSON Schema 行为保持一致。

    Impact

    • 主构造函数中可选的 Kotlin 属性（可空或声明了默认值）不再包含在 JSON Schema 的 `required` 数组中。

    • 使用 @JsonProperty(required = false) 注解的属性，包括未指定 required 的 @JsonProperty 声明，不再被视为必需。

    • 生成的模式现在为基本类型包含 OpenAPI 风格的 ``format` 提示（例如，``int32` 对应 ``int`，``int64` 对应 ``long`，``date-time` 对应 ``LocalDateTime`），以匹配工具调用所使用的格式约定。

    • BeanOutputConverter.postProcessSchema(JsonNode) 扩展点已被移除。覆盖此方法的自定义子类将无法通过编译。

    Migration

    若要自定义 JSON Schema 的生成，请重写BeanOutputConverter.generateSchema()。子类可以通过委托给super.generateSchema()来对默认生成的 Schema 进行后处理。

    // Before
class CustomConverter extends BeanOutputConverter<MyType> {

    CustomConverter() {
        super(MyType.class);
    }

    @Override
    protected void postProcessSchema(JsonNode schema) {
        // mutate schema
    }
}

// After
class CustomConverter extends BeanOutputConverter<MyType> {

    CustomConverter() {
        super(MyType.class);
    }

    @Override
    protected String generateSchema() {
        String schema = super.generateSchema();
        // post-process schema
        return schema;
    }
}

// After

    已移除密封的 MCP 架构接口

    以下接口不再为 sealed： McpSchema.JSONRPCMessage、McpSchema.Request、McpSchema.Result、McpSchema.Notification、 McpSchema.ResourceContents、McpSchema.CompleteReference 和 McpSchema.Content。

    • ToolContext.TOOL_CALL_HISTORY 常量已不再存在

    • ToolContext.getToolCallHistory() 方法已不再存在

    • ToolContext 不再自动填充对话历史。

    为何做出此变更？

    1. 内存效率：防止长对话中内存无限制增长

    2. 关注点分离：工具应基于其参数进行操作，而非管理对话状态。

    3. 架构对齐：对话上下文应归属于顾问层级，而非工具执行层级。

    Migration

    如果您的应用程序需要对话历史管理，请使用ToolCallingAdvisor：

    使用 ToolCallingAdvisor 管理对话历史
    ChatClient chatClient = ChatClient.builder()
    .defaultAdvisors(
        ToolCallingAdvisor.builder()
            .conversationHistoryEnabled(true)  // Full history (default)
            .build()
    )
    .build();

    ToolCallingAdvisor 的工作原理：

    ToolCallingAdvisor 在顾问级别管理对话历史：

    • conversationHistoryEnabled=true（默认值）：保留完整的对话历史，并在工具调用迭代之间将其发送给 LLM，使 LLM 能够结合完整上下文综合结果。

    • conversationHistoryEnabled=false：仅将最新的工具响应发送给 LLM（当 ChatMemory 顾问单独管理历史记录时很有用）

    关键点： 对话历史由 大语言模型（LLM） 用于理解上下文并生成回复，而 工具 本身并不使用对话历史。工具仅接收其输入参数以及您明确提供的任何自定义上下文。

    ToolContext 仍可用于向工具传递自定义的、特定于应用程序的数据：

    向工具传递自定义上下文

    .user("What's the weather in SF?")
    .toolContext(Map.of("userId", "user123", "apiKey", "secret"))
    .call()
    .chatResponse();

    1. 旧金山和洛杉矶的天气如何？

    2. LLM 请求工具调用：getWeather(SF) 和 getWeather(LA)

    3. 工具仅使用其参数执行（不包含对话历史）。

    4. ToolCallingAdvisor 收集工具结果和对话历史。

    5. 大语言模型接收顾问提供的对话上下文，并综合生成：“旧金山的天气为 72°F，洛杉矶则为 85°F。”

    LLM 通过顾问链而非 ToolContext 查看完整的对话。

    AbstractFilterExpressionConverter：doSingleValue 现已变为抽象方法

    在AbstractFilterExpressionConverter（由向量存储过滤器表达式转换器使用）中，方法doSingleValue(Object value, StringBuilder context)已从具体方法更改为抽象方法。现在，扩展AbstractFilterExpressionConverter的自定义向量存储实现必须显式实现此方法。

    Impact

    • 任何自定义的扩展自AbstractFilterExpressionConverter且未重写doSingleValue()的FilterExpressionConverter将无法通过编译。

    • 实现必须将单个过滤值（如 String、Number、Boolean、Date 等）转换为目标格式，并将其追加到提供的 StringBuilder 上下文中。

    Migration

    在您的自定义转换器中实现 `doSingleValue(Object value, StringBuilder context)` 方法。您可以使用提供的静态辅助方法：

    • 基于 JSON 的过滤器（例如 PostgreSQL JSONPath、Neo4j Cypher、Weaviate）：使用 emitJsonValue(Object value, StringBuilder context) 来对值进行序列化，并添加正确的引号和转义。

    • 基于 Lucene 的过滤器（例如 Elasticsearch、OpenSearch、GemFire）：对字符串值使用 emitLuceneString(String value, StringBuilder context)，并根据存储库的查询语法处理其他类型（数字、布尔值、日期）。

    • 其他格式：实现自己的逻辑，并将结果追加到context。

    该框架在调用 doSingleValue 之前会规范化值（例如将 ISO 日期字符串转换为 Date），因此您的实现接收到的已经是经过规范化的值。如果您需要在标准流程之外构建表达式时进行相同的规范化，可以使用静态辅助方法 normalizeDateString(Object)。

    每个 `ChatModel` 实例在构造时，可接受一个可选的 `ChatOptions` 或 `FunctionCallingOptions` 实例，该实例可用于配置调用模型时使用的默认工具。

    • 通过默认 `FunctionCallingOptions` 实例的 `functions()` 方法传递的任何工具，都会被包含在该 `ChatModel` 实例对模型的每次调用中，但可能会被运行时选项覆盖。

    • 通过默认 `FunctionCallingOptions` 实例的 `functionCallbacks()` 方法传递的任何工具，仅可用于运行时动态解析（参见 工具解析），除非显式请求，否则永远不会包含在调用模型的请求中。

    自 1.0.0-M6 版本起：

    • 通过 `functions()` 方法或默认 `FunctionCallingOptions` 实例的 `functionCallbacks()` 传递的任何工具现在都以相同的方式处理：它们会被包含在该 `ChatModel` 实例对模型的每次调用中，并可能由运行时选项覆盖。这样一来，工具被包含在模型调用中的方式保持一致，避免了因 `functionCallbacks()` 与其他所有选项的行为差异而导致的任何混淆。

    1.0.0-M6 版本引入了用于处理工具调用的新 API。除上述情况外，旧版 API 在所有场景中均保持了向后兼容性。旧版 API 仍然可用，但已被弃用，并将在 1.0.0-M7 版本中移除。

    • 一种新的“便携式选项”设计模式。我们希望在不同的基于聊天的 AI 模型之间，尽可能提高ModelCall的便携性。存在一组通用的生成选项，以及特定于模型提供商的选项。采用了一种类似“鸭子类型”的方法。ModelOptions（位于 model 包中）是一个标记接口，表明该类的实现将为模型提供选项。参见ImageOptions，这是一个子接口，定义了所有文本→图像ImageModel实现中的便携式选项。然后，StabilityAiImageOptions和OpenAiImageOptions提供了特定于每个模型提供商的选项。所有选项类均通过流式 API 构建器创建，均可传入便携式的ImageModelAPI。这些选项数据类型用于ImageModel实现的自动配置/配置属性。
