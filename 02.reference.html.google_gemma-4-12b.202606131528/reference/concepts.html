    人工智能概念

    本节介绍了 Spring AI 使用的核心概念。我们建议仔细阅读，以理解 Spring AI 实现背后的思想。

    Models

    AI 模型是旨在处理和生成信息的算法，通常模仿人类的认知功能。 通过从大型数据集中学习模式和见解，这些模型可以做出预测、文本、图像或其他输出，从而增强各行业的各种应用。

    有许多不同类型的 AI 模型，每种模型都适用于特定的使用场景。 虽然 ChatGPT 及其生成式 AI 能力通过文本输入和输出吸引了用户，但许多模型和公司提供了多样化的输入和输出方式。 在 ChatGPT 出现之前，许多人被 Midjourney 和 Stable Diffusion 等文本到图像生成模型所吸引。

    Spring AI 目前支持将输入和输出处理为语言、图像和音频的模型。 在前表中最后一行，该模型接受文本作为输入并输出数字，更常被称为嵌入（embedding）文本，它代表了 AI 模型中使用的内部数据结构。 Spring AI 支持嵌入功能，以实现更高级的使用场景。

    像 GPT 这样的模型之所以与众不同，在于它们的预训练特性，正如 GPT（Chat Generative Pre-trained Transformer）中的“P”所指出的那样。 这种预训练特性将人工智能转变为一种通用的开发工具，不再需要深厚的机器学习或模型训练背景。

    Prompts

    提示词是引导人工智能模型生成特定输出的语言类输入的基石。 对于熟悉 ChatGPT 的用户来说，提示词可能看起来仅仅是输入到对话框中并发送给 API 的文本。 然而，它的内涵远不止于此。 在许多 AI 模型中，提示词的文本并非简单的字符串。

    ChatGPT 的 API 在一个提示词（prompt）中包含多个文本输入，每个文本输入都被分配了一个角色。 例如，有系统角色（system role），它告诉模型如何表现并设定交互的上下文。 还有用户角色（user role），通常是来自用户的输入。

    撰写有效的提示词既是一门艺术，也是一门科学。 ChatGPT 是为人类对话而设计的。 这与使用类似 SQL 来“提问”的做法大相径庭。 人们必须像与另一个人交谈一样与 AI 模型进行沟通。

    这种交互方式的重要性甚至促使“提示工程”（Prompt Engineering）成为了一个独立的学科。 目前已经涌现出一系列旨在提高提示词有效性的技术。 投入时间精心构思提示词可以大幅提升最终的输出效果。

    分享提示词（prompts）已成为一种社区实践，且目前正有活跃的学术研究在围绕这一主题展开。 作为创作有效提示词可能具有多么反直觉的一个例子（例如，与 SQL 形成对比），一项最近的研究论文发现，你最能使用的有效提示词之一是以“深呼吸，并逐步完成此任务”这一短语开头的。 这应该能让你意识到为什么语言如此重要。 我们目前还不完全了解如何最有效地利用这一技术的早期版本（如 ChatGPT 3.5），更不用说那些正在开发中的新版本了。

    提示词模板

    创建有效的提示词包括建立请求的上下文，并将请求中的部分内容替换为用户输入的特定值。

    此过程使用传统的基于文本的模板引擎进行提示词（prompt）的创建和管理。 Spring AI 采用开源库 StringTemplate 来实现这一目的。

    例如，考虑这样一个简单的提示词模板：

    Tell me a {adjective} joke about {content}.

    在 Spring AI 中，提示词模板（prompt templates）可以类比为 Spring MVC 架构中的“View”。 提供一个模型对象（通常是 java.util.Map）来填充模板中的占位符。 “渲染后”的字符串将成为提供给 AI 模型的提示词内容。

    发送给模型的提示词（prompt）的具体数据格式存在显著差异。 提示词最初只是简单的字符串，现已演变为包含多个消息的结构，其中每个消息中的每个字符串都代表模型的一个特定角色。

    Embeddings

    嵌入（Embeddings）是文本、图像或视频的数值表示，用于捕捉输入内容之间的关系。

    Embedding 的工作原理是将文本、图像和视频转换为由浮点数组成的数组，称为向量（vectors）。 这些向量旨在捕捉文本、图像和视频的含义。 Embedding 数组的长度被称为向量的维度（dimensionality）。

    通过计算两段文本的向量表示之间的数值距离，应用程序可以确定生成这些嵌入向量的对象之间的相似度。

    作为一名探索人工智能的 Java 开发者，并不需要理解这些向量表示背后的复杂数学理论或具体的实现细节。 只要能够基本了解它们在 AI 系统中的作用和功能就足够了，尤其是在您将 AI 功能集成到应用程序中时。

    Embeddings 在检索增强生成（RAG）模式等实际应用中尤为相关。 它们能够将数据表示为语义空间中的点，这类似于欧几里得几何中的二维空间，但处于更高维度。 这意味着，正如欧几里得几何中平面上的点可以根据坐标的远近而靠近或远离一样，在语义空间中，点的接近程度反映了意义上的相似性。 关于相似主题的句子在这个多维空间中位置更接近，就像图表上彼此靠近的点一样。 这种接近性有助于文本分类、语义搜索甚至产品推荐等任务，因为它允许人工智能根据这些概念在扩展的语义景观中的“位置”来识别并归类相关概念。

    你可以将这个语义空间视为一个向量。

    Tokens

    Token 是 AI 模型运作的基础构建块。 在输入时，模型将单词转换为 Token；在输出时，它们将 Token 转换回单词。

    在英语中，一个 token 大约对应单词的 75%。作为参考，莎士比亚的全部作品总计约 900,000 个单词，折合约为 120 万个 token。

    或许更重要的一点是：Token = 金钱。 在托管 AI 模型的情境下，您的费用是由所使用的 Token 数量决定的。输入和输出都会计入总的 Token 数量。

    此外，模型受限于 Token 限制，这限制了单次 API 调用中可处理的文本数量。 这一阈值通常被称为“上下文窗口”。模型不会处理任何超过此限制的文本。

    例如，ChatGPT3 有 4K token 的限制，而 GPT4 提供多种选项，如 8K、16K 和 32K。 Anthropic 的 Claude AI 模型具有 100K token 的限制，而 Meta 最近的研究产出了一个拥有 1M token 限制的模型。

    若要使用 GPT-4 总结莎士比亚的文集，您需要制定软件工程策略来切分数据，并确保数据能够呈现在模型的上下文窗口限制之内。 Spring AI 项目可以帮助您完成这项任务。

    结构化输出

    AI 模型输出的内容传统上是以 java.lang.String 形式呈现的，即使你要求以 JSON 格式返回。 它可能是一个正确的 JSON 字符串，但它并不是一个 JSON 数据结构。它仅仅是一个字符串。 此外，在提示词中要求“提供 JSON”也不完全准确。

    这种复杂性导致了一个专门领域的出现，该领域涉及创建提示词以获得预期的输出，随后将生成的简单字符串转换为可用于应用程序集成的可用数据结构。

    结构化输出转换采用了精心设计的提示词，通常需要与模型进行多次交互才能达到所需的格式。

    将您的数据和 API 引入 AI 模型

    您可以通过哪些方式为 AI 模型提供其未经过训练的信息？

    请注意，GPT 3.5/4.0 数据集仅更新至 2021 年 9 月。 因此，对于需要超出该日期知识的问题，模型会表示不知道答案。 一个有趣的冷知识是，这个数据集的大小约为 650GB。

    有三种技术可用于定制 AI 模型以纳入您的数据：

    • 微调 (Fine Tuning)：这种传统的机器学习技术涉及对模型进行定制并更改其内部权重。 然而，对于机器学习专家来说这是一个具有挑战性的过程，且由于 GPT 等模型的规模庞大，该过程极其消耗资源。此外，某些模型可能不提供此选项。

    • Prompt Stuffing：一种更实用的替代方案是将您的数据嵌入到提供给模型的提示词中。考虑到模型的 token 限制，需要采用相关技术在模型的上下文窗口内呈现相关数据。 这种方法在口语中被称为“stuffing the prompt”。 Spring AI 库可以帮助您实现基于“stuffing the prompt”技术的解决方案，该技术也被称为 检索增强生成 (RAG)。

    • Tool Calling：此技术允许注册工具（用户定义的服务），将大语言模型连接到外部系统的 API。 Spring AI 大大简化了您需要编写的用于支持 tool calling 的代码。

    检索增强生成

    一种被称为检索增强生成（Retrieval Augmented Generation，简称 RAG）的技术应运而生，旨在解决将相关数据纳入提示词以获得准确的 AI 模型响应这一挑战。

    该方法涉及一种批处理风格的编程模型，其中作业从您的文档中读取非结构化数据，对其进行转换，然后将其写入向量数据库。 从高层视角来看，这是一个 ETL（提取、转换和加载）流水线。 向量数据库用于 RAG 技术中的检索部分。

    作为将非结构化数据加载到向量数据库的一部分，最重要的转换之一是将原始文档拆分为更小的片段。 将原始文档拆分为更小片段的过程包含两个重要步骤：

    1. 在分割文档时，请保留内容的语义边界。 例如，对于包含段落和表格的文档，应避免在段落或表格中间进行分割。 对于代码，应避免在方法的实现过程中进行分割。

    2. 将文档的各个部分进一步拆分为更小的部分，使其大小仅占 AI 模型 Token 限制的一小部分。

    RAG 的下一个阶段是处理用户输入。 当用户的提问需要由 AI 模型回答时，问题以及所有“相似”的文档片段都会被放入发送给 AI 模型的提示词（prompt）中。 这就是使用向量数据库的原因。它非常擅长寻找相似内容。

    • ETL Pipeline 提供了关于编排从数据源提取数据并将其存储到结构化向量库流程的进一步信息，确保在将数据传递给 AI 模型时，数据处于最适合检索的格式。

    • ChatClient - RAG 解释了如何使用 QuestionAnswerAdvisor 在您的应用程序中启用 RAG 功能。

    工具调用

    大型语言模型（LLMs）在训练完成后即被冻结，导致知识陈旧，且它们无法访问或修改外部数据。

    Tool Calling 机制解决了这些不足。 它允许您将自己的服务注册为工具，从而将大语言模型与外部系统的 API 连接起来。 这些系统可以为 LLM 提供实时数据，并代表它们执行数据处理操作。

    Spring AI 大大简化了支持工具调用（tool invocation）所需的代码。 它会为您处理工具调用的对话逻辑。 您可以将工具作为带有 @Tool 注解的方法提供，并在提示词选项中提供它，使其可供模型使用。 此外，您可以在单个提示词中定义并引用多个工具。

    1. 当我们想要让模型可以使用某个工具时，我们会将该工具的定义包含在聊天请求中。每个工具定义都由名称、描述以及输入参数的架构（schema）组成。

    2. 当模型决定调用工具时，它会发送一个包含工具名称和根据定义架构建模的输入参数的响应。

    3. 该应用程序负责使用工具名称来识别并执行带有提供的输入参数的工具。

    4. 工具调用的结果由应用程序处理。

    5. 应用程序将工具调用结果发送回模型。

    6. 模型使用工具调用结果作为额外上下文来生成最终响应。

    请参阅 Tool Calling 文档，了解有关如何在不同 AI 模型中使用此功能的更多信息。

    评估 AI 回复

    有效评估人工智能系统对用户请求的输出，对于确保最终应用的准确性和实用性至关重要。 几种新兴技术使得利用预训练模型本身来实现这一目的成为可能。

    此评估过程涉及分析生成的回答是否符合用户的意图以及查询的上下文。相关性、连贯性和事实准确性等指标被用于衡量 AI 生成回答的质量。

    一种方法是将用户的请求和 AI 模型的回答同时呈现给模型，查询该回答是否与提供的数据一致。

    此外，利用向量数据库中存储的信息作为补充数据可以增强评估过程，有助于判断回答的相关性。

    Spring AI 项目提供了一个 Evaluator API，目前可用于访问评估模型响应的基础策略。 请参阅 Evaluation Testing 文档以获取更多信息。
