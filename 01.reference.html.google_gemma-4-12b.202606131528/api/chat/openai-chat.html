    OpenAI 对话

    Spring AI 支持来自 OpenAI 的各种 AI 语言模型。OpenAI 是 ChatGPT 背后的公司，由于其创建了行业领先的文本生成模型和嵌入模型，在激发人们对 AI 驱动的文本生成的兴趣方面发挥了重要作用。

    从版本 2.0.0-M5 开始，Spring AI 在底层为所有 OpenAI 模型使用官方的 openai-java SDK。此次过渡预计是无缝的，对于现有 OpenAI API 属性和构建器的用户来说，不会有任何破坏性变更。如果您发现任何问题，请通过 Spring AI GitHub Issues 向我们报告。

    Prerequisites

    您需要创建一个 OpenAI API，以访问 ChatGPT 模型。

    在 OpenAI 注册页面 创建一个账户，并在 API Keys 页面 生成 token。

    Spring AI 项目定义了一个名为 spring.ai.openai.api-key 的配置属性，您应当将其设置为从 openai.com 获取的 API Key 值。

    您可以在您的 application.properties 文件中设置此配置属性：

    spring.ai.openai.api-key=<your-openai-api-key>

    为了在处理 API 密钥等敏感信息时增强安全性，您可以使用 Spring Expression Language (SpEL) 来引用自定义的环境变量：

    # In application.yml
spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
    # In your environment or .env file
export OPENAI_API_KEY=<your-openai-api-key>

    您也可以在应用程序代码中通过编程方式设置此配置：

    // Retrieve API key from a secure source or environment variable
String apiKey = System.getenv("OPENAI_API_KEY");

    添加仓库和 BOM

    Spring AI 的制品发布在 Maven Central 和 Spring Snapshot 仓库中。 请参阅 Artifact Repositories 部分，将这些仓库添加到您的构建系统中。

    为了帮助管理依赖，Spring AI 提供了一个 BOM（物料清单），以确保整个项目中使用一致的 Spring AI 版本。请参阅 Dependency Management 部分将 Spring AI BOM 添加到您的构建系统中。

    Auto-configuration

    Spring AI 的自动配置中，starter 模块的 artifact 名称发生了重大变化。 请参阅 升级说明 获取更多信息。

    Spring AI 为 OpenAI Chat Client 提供 Spring Boot 自动配置。 若要启用它，请将以下依赖添加到您项目的 Maven pom.xml 或 Gradle build.gradle 构建文件中：

    • Maven

    • Gradle

    <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>
    dependencies {
    implementation 'org.springframework.ai:spring-ai-starter-model-openai'
}
    请参阅 Dependency Management 部分，将 Spring AI BOM 添加到您的构建文件中。

    前缀 spring.ai.retry 用作属性前缀，允许您配置 OpenAI 对话模型的重试机制。

    Property Description Default

    spring.ai.retry.max-attempts

    最大重试次数。

    10

    spring.ai.retry.backoff.initial-interval

    指数退避策略的初始睡眠时长。

    2 秒

    spring.ai.retry.backoff.multiplier

    退避间隔乘数。

    5

    spring.ai.retry.backoff.max-interval

    最大退避时长。

    3 分钟。

    spring.ai.retry.on-client-errors

    如果为 false，则抛出 NonTransientAiException，并且不要尝试重试 4xx 客户端错误代码。

    false

    spring.ai.retry.exclude-on-http-codes

    不应触发重试的 HTTP 状态码列表（例如，用于抛出 NonTransientAiException）。

    empty

    spring.ai.retry.on-http-codes

    应触发重试的 HTTP 状态码列表（例如，用于抛出 TransientAiException）。

    empty

    连接属性

    前缀 spring.ai.openai 被用作属性前缀，让您能够连接到 OpenAI。

    Property Description Default

    spring.ai.openai.base-url

    连接的 URL

    api.openai.com

    spring.ai.openai.api-key

    API 密钥

    -

    spring.ai.openai.organization-id

    您可以选择指定用于 API 请求的组织。

    -

    spring.ai.openai.project-id

    您可以选择指定用于 API 请求的项目。

    -
    对于属于多个组织（或通过其旧版用户 API 密钥访问项目）的用户，您可以选择性地指定用于 API 请求的组织和项目。 这些 API 请求的使用量将计入所指定的组织和项目。

    User-Agent 请求头

    Spring AI 会在发送给 OpenAI 的所有请求中自动包含一个 User-Agent: spring-ai 请求头。 这有助于 OpenAI 为了分析和支持目的识别来自 Spring AI 的请求。 此请求头是自动发送的，Spring AI 用户无需进行任何配置。

    如果您是正在构建兼容 OpenAI 服务的 API 提供商，您可以通过读取服务器上接收到的请求中的 User-Agent HTTP 请求头来追踪 Spring AI 的使用情况。

    配置属性

    启用和禁用聊天自动配置现在通过带有前缀 spring.ai.model.chat 的顶级属性进行配置。

    若要启用，请设置 spring.ai.model.chat=openai（默认已启用）

    若要禁用，请设置 spring.ai.model.chat=none（或任何不匹配 openai 的值）

    此更改是为了支持配置多个模型。

    前缀 spring.ai.openai.chat 是用于配置 OpenAI 的聊天模型实现的属性前缀。

    Property Description Default

    spring.ai.openai.chat.enabled（已移除且不再有效）

    启用 OpenAI 对话模型。

    true

    spring.ai.model.chat

    启用 OpenAI 对话模型。

    openai

    spring.ai.openai.chat.base-url

    spring.ai.openai.base-url 属性的可选覆盖项，用于提供特定于对话的 URL。

    -

    spring.ai.openai.chat.api-key

    spring.ai.openai.api-key 的可选覆盖项，用于提供特定于对话的 API Key。

    -

    spring.ai.openai.chat.organization-id

    您可以选择指定用于 API 请求的组织。

    -

    spring.ai.openai.chat.project-id

    您可以选择指定用于 API 请求的项目。

    -

    spring.ai.openai.chat.model

    要使用的 OpenAI 对话模型名称。您可以选择如下模型：gpt-5-mini、gpt-4o、gpt-4o-mini、gpt-4-turbo、gpt-3.5-turbo 等。更多信息请参阅 models 页面。

    gpt-5-mini

    spring.ai.openai.chat.temperature

    用于控制生成补全内容表观创造性的采样温度。较高的值会使输出更具随机性，而较低的值则会使结果更集中且具有确定性。不建议在同一个补全请求中同时修改 temperature 和 top_p，因为这两个设置之间的相互作用难以预测。

    0.8

    spring.ai.openai.chat.frequency-penalty

    介于 -2.0 和 2.0 之间的数值。正值会根据新 token 在文本中已出现的频率对其进行惩罚，从而降低模型逐字重复同一行内容的概率。

    0.0f

    spring.ai.openai.chat.logit-bias

    修改指定 token 出现在补全内容中的概率。

    -

    spring.ai.openai.chat.max-tokens

    在聊天补全中可生成的最大 token 数量。输入 token 和生成 token 的总长度受限于模型的上下文长度。用于非推理模型（例如 gpt-4o, gpt-3.5-turbo）。不可与推理模型配合使用（例如 o1, o3, o4-mini 系列）。与 maxCompletionTokens 互斥——同时设置两者将导致 API 错误。

    -

    spring.ai.openai.chat.max-completion-tokens

    可用于补全生成的 token 数量上限，包括可见输出 token 和推理 token。推理模型必填（例如 o1、o3、o4-mini 系列）。不可用于非推理模型（例如 gpt-4o、gpt-3.5-turbo）。与 maxTokens 互斥——同时设置两者将导致 API 错误。

    -

    spring.ai.openai.chat.n

    为每条输入消息生成多少个聊天补全选项。请注意，您将根据所有选项中生成的 token 总数计费。请将 n 保留在 1 以最小化成本。

    1

    spring.ai.openai.chat.store

    是否将此对话补全请求的输出存储以用于我们的模型训练

    false

    spring.ai.openai.chat.metadata

    用于在聊天完成仪表板中过滤完成结果的开发者自定义标签和值

    空映射

    spring.ai.openai.chat.output-modalities

    输出您希望模型针对此请求生成的类型。大多数模型都能够生成文本，这是默认选项。 gpt-audio 模型还可以用于生成音频。若要请求该模型同时生成文本和音频响应， 您可以使用：text、audio。不支持流式传输。

    -

    spring.ai.openai.chat.output-audio

    用于音频生成的音频参数。当请求的 output-modalities 为 audio 时需要提供。 需要使用 gpt-audio 模型，且不支持流式输出（streaming completions）。

    -

    spring.ai.openai.chat.presence-penalty

    介于 -2.0 和 2.0 之间的数值。正值会根据新标记（tokens）是否出现在之前的文本中来对其进行惩罚，从而增加模型谈论新话题的概率。

    -

    spring.ai.openai.chat.response-format.type

    兼容 GPT-4o、GPT-4o mini、GPT-4 Turbo 以及所有更新于 gpt-3.5-turbo-1106 的 GPT-3.5 Turbo 模型。JSON_OBJECT 类型启用 JSON 模式，确保模型生成的消息是有效的 JSON。 JSON_SCHEMA 类型启用 Structured Outputs，确保模型将符合您提供的 JSON schema。JSON_SCHEMA 类型还要求同时设置 responseFormat.schema 属性。

    -

    spring.ai.openai.chat.response-format.name

    响应格式架构名称。仅适用于 responseFormat.type=JSON_SCHEMA

    custom_schema

    spring.ai.openai.chat.response-format.schema

    响应格式 JSON 架构。仅适用于 responseFormat.type=JSON_SCHEMA

    -

    spring.ai.openai.chat.response-format.strict

    JSON Schema 符合性的响应格式严格程度。仅适用于 responseFormat.type=JSON_SCHEMA

    -

    spring.ai.openai.chat.seed

    此功能处于 Beta 测试阶段。如果指定了种子，我们的系统将尽力进行确定性采样，使得使用相同种子和参数的重复请求应返回相同的结果。

    -

    spring.ai.openai.chat.stop

    最多 4 个序列，API 将停止生成后续 token。

    -

    spring.ai.openai.chat.top-p

    一种替代温度采样（sampling with temperature）的方法称为核采样（nucleus sampling），其中模型会考虑概率质量在 top_p 以内的 token 结果。因此，0.1 意味着仅考虑包含前 10% 概率质量的 token。我们通常建议修改其中之一或 temperature，但不要同时修改两者。

    -

    spring.ai.openai.chat.tools

    模型可调用的工具列表。目前仅支持函数作为工具。请使用此项提供模型可能生成 JSON 输入的函数列表。

    -

    spring.ai.openai.chat.tool-choice

    控制模型调用哪个（如果有的话）函数。none 表示模型不会调用函数，而是生成消息。auto 表示模型可以在生成消息和调用函数之间进行选择。通过 {"type: "function", "function": {"name": "my_function"}} 指定特定函数会强制模型调用该函数。如果没有提供任何函数，默认值为 none。如果存在函数，默认值为 auto。

    -

    spring.ai.openai.chat.user

    代表您的终端用户的唯一标识符，可帮助 OpenAI 进行监控和滥用检测。

    -

    spring.ai.openai.chat.stream-usage

    （仅限流式传输）设置为添加一个包含整个请求的 token 使用统计数据的额外数据块。此数据块的 choices 字段为空数组，且所有其他数据块也将包含一个 usage 字段，但其值为 null。

    false

    spring.ai.openai.chat.parallel-tool-calls

    在工具使用过程中是否启用并行函数调用。

    true

    spring.ai.openai.chat.prompt-cache-key

    OpenAI 用于优化相似请求缓存命中率的缓存键。它能改善延迟并降低成本。它取代了用于缓存目的且已弃用的 user 字段。了解更多信息。

    -

    spring.ai.openai.chat.safety-identifier

    一个稳定的标识符，用于帮助 OpenAI 检测违反使用政策的用户。应为哈希值（例如：哈希处理后的用户名或电子邮件）。它取代了已弃用的 user 字段，用于安全追踪。了解更多信息。

    -

    spring.ai.openai.chat.http-headers

    可添加到聊天补全请求中的可选 HTTP 请求头。若要覆盖 api-key，您需要使用 Authorization 请求头键，并且必须在键值前加上 Bearer 前缀。

    -

    spring.ai.openai.chat.tool-callbacks

    用于与 ChatModel 注册的工具回调（Tool Callbacks）。

    -

    spring.ai.openai.chat.service-tier

    指定用于处理请求的处理类型。

    -

    spring.ai.openai.chat.extra-body

    包含在请求中的附加参数。接受任何被扁平化到 JSON 请求顶层的键值对。旨在用于支持超出标准 OpenAI API 参数的 OpenAI 兼容服务器（如 vLLM、Ollama 等）。官方 OpenAI API 会以 400 错误拒绝未知参数。详情请参阅 在 OpenAI 兼容服务器中使用额外参数。

    -

    当使用暴露 OpenAI 兼容 API 的本地 Docker Model Runner 时，如果服务器要求，您可能需要在基础 URL 后添加 /v1。 例如：使用 spring.ai.openai.chat.base-url=http://localhost:12434/engines/v1 而不是 localhost:12434/engines。

    在使用 gpt-5、gpt-5-mini 和 gpt-5-nano 等 GPT-5 模型时，不支持 temperature 参数。 这些模型针对推理进行了优化，不使用 temperature。 指定 temperature 值将导致错误。 相比之下，像 gpt-5-chat 这样的对话模型支持 temperature 参数。
    您可以为 和 的实现覆盖通用的 和 。 如果设置了 和 属性，它们将优先于通用属性。 如果您希望为不同的模型和不同的模型端点使用不同的 OpenAI 账号，这将非常有用。
    所有以 spring.ai.openai.chat 为前缀的属性都可以通过在 Prompt 调用中添加特定于请求的 运行时选项 (Runtime Options) 来在运行时覆盖。

    Token 限制参数：模型特定用法

    OpenAI 提供两个互斥的参数来控制 Token 生成限制：

    参数 使用场景 兼容型号

    maxTokens

    非推理模型

    gpt-4o, gpt-4o-mini, gpt-4-turbo, gpt-3.5-turbo

    maxCompletionTokens

    推理模型

    o1, o1-mini, o1-preview, o3, o4-mini 系列
    这些参数是互斥的。同时设置两者将导致 OpenAI 返回 API 错误。

    使用示例

    对于非推理模型 (gpt-4o, gpt-3.5-turbo)：

    ChatResponse response = chatModel.call(
    new Prompt(
        "Explain quantum computing in simple terms.",
        OpenAiChatOptions.builder()
            .model("gpt-4o")
            .maxTokens(150)  // Use maxTokens for non-reasoning models
        .build()
    ));

    对于推理模型（o1、o3 系列）：

    ChatResponse response = chatModel.call(
    new Prompt(
        "Solve this complex math problem step by step: ...",
        OpenAiChatOptions.builder()
            .model("o1-preview")
            .maxCompletionTokens(1000)  // Use maxCompletionTokens for reasoning models
        .build()
    ));

    Builder 模式验证： OpenAI ChatOptions 构建器会自动强制执行“最后设置生效”的互斥机制：

    // This will automatically clear maxTokens and use maxCompletionTokens
OpenAiChatOptions options = OpenAiChatOptions.builder()
    .maxTokens(100)           // Set first
    .maxCompletionTokens(200) // This clears maxTokens and logs a warning
    .build();

// Result: maxTokens = null, maxCompletionTokens = 200

    运行时选项

    OpenAiChatOptions.java 类提供了模型配置，例如要使用的模型、temperature（温度）、frequency penalty（频率惩罚）等。

    在启动时，可以通过 OpenaiChatModel(api, options) 构造函数或 spring.ai.openai.chat.* 属性来配置默认选项。

    在运行时，您可以通过在 Prompt 调用中添加新的、特定于请求的选项来覆盖默认选项。 例如，若要为特定请求覆盖默认模型和 temperature：

    ChatResponse response = chatModel.call(
    new Prompt(
        "Generate the names of 5 famous pirates.",
        OpenAiChatOptions.builder()
            .model("gpt-4o")
            .temperature(0.4)
        .build()
    ));
    除了特定模型的 OpenAiChatOptions，您还可以使用通过 ChatOptions#builder() 创建的通用 ChatOptions 实例。

    函数调用

    您可以在 OpenAiChatModel 中注册自定义的 Java 函数，并让 OpenAI 模型智能选择输出包含调用一个或多个已注册函数的参数的 JSON 对象。 这是将 LLM 能力与外部工具和 API 连接的一种强大技术。 阅读更多关于 Tool Calling 的内容。

    OpenAiChatModel 不在内部执行工具调用。 工具执行必须通过以下两种支持的方法之一在外部处理：

    • 带有 ToolCallingAdvisor 的 ChatClient —— 这是大多数用例的推荐方法。ToolCallingAdvisor 在存在工具时会自动注册，并透明地管理工具调用循环。

    • 用户控制的工具执行 — 当您需要完全控制循环时（例如，当将工具调用与直接访问 ChatModel 结合使用时），请直接使用 DefaultToolCallingManager。

    通过 ChatClient 进行工具调用（推荐）

    无论是同步还是流式工具执行，均使用 ChatClient。 当存在工具时，ToolCallingAdvisor 会自动注册，因此不需要显式的顾问配置。

    ToolCallback weatherCallback = FunctionToolCallback.builder("getCurrentWeather", new WeatherService())
    .description("Get the weather in location")
    .inputType(WeatherService.Request.class)
    .build();

// Synchronous
String response = ChatClient.create(chatModel)
    .prompt()
    .user("What's the weather in Paris, Tokyo, and New York?")
    .tools(weatherCallback)
    .call()
    .content();

// Streaming
Flux<String> stream = ChatClient.create(chatModel)
    .prompt()
    .user("What's the weather in Paris, Tokyo, and New York?")
    .tools(weatherCallback)
    .stream()
    .content();

    用户控制的工具执行

    当您需要直接访问 ChatModel API 并希望完全控制工具调用循环（tool-call loop）时，请使用此模式。 直接调用 ChatModel 而不使用 ToolCallingAdvisor；自行检查工具调用，并使用 ToolCallingManager 来驱动循环。

    ToolCallingManager toolCallingManager = ToolCallingManager.builder().build();

OpenAiChatOptions options = OpenAiChatOptions.builder()
    .toolCallbacks(ToolCallbacks.from(new WeatherService()))
    .build();

Prompt prompt = new Prompt("What's the weather in Paris, Tokyo, and New York?", options);
ChatResponse response = chatModel.call(prompt);

while (response.hasToolCalls()) {
    ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, response);
    prompt = new Prompt(result.conversationHistory(), options);
    response = chatModel.call(prompt);
}

    对于流式传输，使用 MessageAggregator 聚合每个流式响应，以检测跨分块的工具调用：

    AtomicReference<ChatResponse> aggregatedRef = new AtomicReference<>();
new MessageAggregator()
    .aggregate(chatModel.stream(prompt), aggregatedRef::set)
    .collectList().block();

while (aggregatedRef.get().hasToolCalls()) {
    ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, aggregatedRef.get());
    prompt = new Prompt(result.conversationHistory(), options);
    aggregatedRef.set(null);
    new MessageAggregator()
        .aggregate(chatModel.stream(prompt), aggregatedRef::set)
        .collectList().block();
}

String content = aggregatedRef.get().getResult().getOutput().getText();

    结构化输出

    OpenAI 提供自定义的 Structured Outputs API，确保您的模型生成的响应严格符合您提供的 JSON Schema。 除了现有的 Spring AI 模型无关的 Structured Output Converter 外，这些 API 还提供了更强的控制力和精确度。

    目前，OpenAI 支持 JSON Schema 语言的一个子集 格式。

    Configuration

    Spring AI 允许您通过使用 OpenAiChatOptions 构建器进行程序化配置，或通过应用程序属性来配置您的响应格式。

    使用聊天选项构建器

    您可以通过如下所示的 OpenAiChatOptions 构建器以编程方式设置响应格式：

    String jsonSchema = """
        {
            "type": "object",
            "properties": {
                "steps": {
                    "type": "array",
                    "items": {
                        "type": "object",
                        "properties": {
                            "explanation": { "type": "string" },
                            "output": { "type": "string" }
                        },
                        "required": ["explanation", "output"],
                        "additionalProperties": false
                    }
                },
                "final_answer": { "type": "string" }
            },
            "required": ["steps", "final_answer"],
            "additionalProperties": false
        }
        """;

Prompt prompt = new Prompt("how can I solve 8x + 7 = -23",
        OpenAiChatOptions.builder()
            .model(ChatModel.GPT_4_O_MINI)
            .responseFormat(new ResponseFormat(ResponseFormat.Type.JSON_SCHEMA, this.jsonSchema))
            .build());

ChatResponse response = this.openAiChatModel.call(this.prompt);
    遵循 OpenAI 的 JSON Schema 语言子集 格式。

    与 BeanOutputConverter 工具集成

    您可以利用现有的 BeanOutputConverter 工具，从您的领域对象中自动生成 JSON Schema，并随后将结构化响应转换为特定领域的实例：

    • Java

    • Kotlin

    record MathReasoning(
    @JsonProperty(required = true, value = "steps") Steps steps,
    @JsonProperty(required = true, value = "final_answer") String finalAnswer) {

    record Steps(
        @JsonProperty(required = true, value = "items") Items[] items) {

        record Items(
            @JsonProperty(required = true, value = "explanation") String explanation,
            @JsonProperty(required = true, value = "output") String output) {
        }
    }
}

var outputConverter = new BeanOutputConverter<>(MathReasoning.class);

var jsonSchema = this.outputConverter.getJsonSchema();

        OpenAiChatOptions.builder()

            .responseFormat(new ResponseFormat(ResponseFormat.Type.JSON_SCHEMA, this.jsonSchema))
            .build());

ChatResponse response = this.openAiChatModel.call(this.prompt);
String content = this.response.getResult().getOutput().getText();

MathReasoning mathReasoning = this.outputConverter.convert(this.content);
    data class MathReasoning(
	val steps: Steps,
	@get:JsonProperty(value = "final_answer") val finalAnswer: String) {

	data class Steps(val items: Array<Items>) {

		data class Items(
			val explanation: String,
			val output: String)
	}
}

val outputConverter = BeanOutputConverter(MathReasoning::class.java)

val jsonSchema = outputConverter.jsonSchema;

val prompt = Prompt("how can I solve 8x + 7 = -23",
	OpenAiChatOptions.builder()
		.model(ChatModel.GPT_4_O_MINI)
		.responseFormat(ResponseFormat(ResponseFormat.Type.JSON_SCHEMA, jsonSchema))

val content = response.getResult().getOutput().getText()

    示例控制器

    创建一个新的 Spring Boot 项目，并将 spring-ai-starter-model-openai 添加到您的 pom（或 gradle）依赖中。

    在 src/main/resources 目录下添加一个 application.properties 文件，以启用并配置 OpenAi 对话模型：

    spring.ai.openai.api-key=YOUR_API_KEY
spring.ai.openai.chat.model=gpt-4o
spring.ai.openai.chat.temperature=0.7
    将 api-key 替换为您自己的 OpenAI 凭据。

    这将创建一个 OpenaiChatModel 实现，您可以将其注入到您的类中。 这是一个使用该聊天模型进行文本生成的简单 @RestController 类示例。

    @RestController
public class ChatController {

    private final OpenAiChatModel chatModel;

    @Autowired
    public ChatController(OpenAiChatModel chatModel) {
        this.chatModel = chatModel;
    }

    @GetMapping("/ai/generate")
    public Map<String,String> generate(@RequestParam(value = "message", defaultValue = "Tell me a joke") String message) {
        return Map.of("generation", this.chatModel.call(message));
    }

    @GetMapping("/ai/generateStream")
	public Flux<ChatResponse> generateStream(@RequestParam(value = "message", defaultValue = "Tell me a joke") String message) {
        Prompt prompt = new Prompt(new UserMessage(message));
        return this.chatModel.stream(prompt);
    }
}

    <dependency>

    API 密钥管理

    Spring AI 通过 ApiKey 接口及其实现类提供灵活的 API 密钥管理。默认实现类 SimpleApiKey 适用于大多数使用场景，但您也可以为更复杂的场景创建自定义实现。

// Build the ChatClient using the custom chat model

    • 动态轮换 API 密钥

    • 实现自定义 API 密钥选择逻辑

    Observability

    Spring AI 在每次调用 OpenAI 时，会在两个层级发出 Micrometer 观测数据：

    • Chat-model 层。 一个 gen_ai.client.operation 观测值会包裹对 OpenAiChatModel.call(…​) 或 .stream(…​) 的每一次调用，并携带请求参数、响应元数据以及 token 使用情况。请参阅 可观测性参考 以获取完整的标签和指标列表。

    • HTTP 层。 一个 okhttp.requests 观测项封装了每一次对 OpenAI API 的 HTTP 请求，携带 HTTP 方法、URI、状态码和异常标签。每个请求还会在传输过程中向任何下游服务（AI 网关、兼容 OpenAI 的推理服务器、代理）传递 traceparent。

    在包含 spring-boot-starter-actuator 和追踪桥接器（micrometer-tracing-bridge-otel 或 micrometer-tracing-bridge-brave）的 Spring Boot 应用程序中，两个层级都会自动连接——无需手动开启。 对于非 Boot 应用程序，请将 ObservationRegistry 传递给 OpenAiChatModel.builder()：

    OpenAiChatModel chatModel = OpenAiChatModel.builder()
    .options(...)
    .observationRegistry(observationRegistry)
    .build();

    连接池指标（可选启用）

    Spring AI 还可以将 OkHttp 连接池指标（带有 state=active|idle 和 client.kind=sync|async 的 okhttp.pool.connection.count）绑定到应用程序的 MeterRegistry。 这些是次要遥测数据——对于容量调优很有用，但对于链路追踪或单次请求延迟并非必需——因此它们默认处于禁用状态。

    要在 Spring Boot 应用程序中启用它们：

    spring.ai.openai.chat.connection-pool-metrics-enabled=true

    对于非 Boot 应用程序，请直接将 MeterRegistry 传递给 builder；只要提供了 registry，gauge 就会绑定：

    OpenAiChatModel chatModel = OpenAiChatModel.builder()
    .options(...)
    .observationRegistry(observationRegistry)
    .meterRegistry(meterRegistry)
    .build();

    HTTP 调度器执行器（高级）

    默认情况下，Spring AI 管理 OkHttp 的 dispatcher 执行器——这是一个平台线程的无界池，复制了 SDK 的默认行为。 对于具有高 HTTP 并发量的负载，或者为了利用 Java 21+ 的虚拟线程，您可以提供自定义的 ExecutorService：

    OpenAiChatModel chatModel = OpenAiChatModel.builder()
    .options(...)
    .dispatcherExecutor(Executors.newVirtualThreadPerTaskExecutor())
    .build();

    相同的 executor 同时支持同步和异步（流式）客户端。 当您提供自己的 executor 时，您负责其生命周期——Spring AI 永远不会对其调用 shutdown()。 如果省略该参数，系统将自动创建并清理内部 executor。

    流式 HTTP 观测（Streaming HTTP observations）未归属于 chat-model 观测

    对于同步调用，okhttp.requests 跨度正确嵌套在 gen_ai.client.operation 跨度之下——完整的追踪树按预期生成。

    对于流式调用，okhttp.requests span 会触发并记录在注册表中，计时器记录在 MeterRegistry 中，且 traceparent 仍会传播到出站请求中——但该 span 并未嵌套在 chat-model span 下。 这是因为 OpenAI SDK 的异步流式实现会在调用 Spring AI 的 HTTP 客户端之前跳转到 ForkJoinPool.commonPool()，从而在那个边界处丢失了调用线程的观测上下文（observation context）。 Spring AI 无法在其 HTTP 客户端包装器内部恢复该上下文。

    如果您需要在追踪 UI 中将流式 HTTP spans 与其父级 chat-model span 相关联，请按 span 名称 okhttp.requests 且 host 为 api.openai.com 进行过滤，并根据 trace ID 或时间戳范围与相应的 gen_ai.client.operation span 进行关联。 针对流式传输的内置父级链接功能正在 OpenAI Java SDK 的上游进行开发中。

    自定义 HTTP 客户端

    Spring AI 在底层使用官方的 openai-java SDK，并使用由 SpringAiOpenAiHttpClient.Builder 构建的自定义 OkHttp 客户端来配置其 HTTP 传输。 您可以通过暴露一个或多个 OpenAiHttpClientBuilderCustomizer 类型的 Bean，在底层的 OkHttpClient 创建之前拦截该构建器。 每个自定义器都会接收到所有 OpenAI 模型（chat、embedding、image、audio、moderation）所使用的相同构建器，因此自定义配置将统一应用于所有模型。

    @FunctionalInterface
public interface OpenAiHttpClientBuilderCustomizer {
    void customize(SpringAiOpenAiHttpClient.Builder builder);
}

    典型使用场景包括：

    • 注册 OkHttp Interceptor 实例（身份验证、传播请求头、自定义日志）；

    • 更换调度器 ExecutorService（例如，用于通过虚拟线程路由异步 I/O）；

    • 配置由 builder 暴露的代理、SSL、主机名验证或连接池大小。

    当存在多个自定义器时，它们将按照 @Order / Ordered 顺序在 Spring AI 自带的默认设置之后应用，从而确保用户代码优先。

    当通过 OpenAi*Model.Builder 手动连接模型时，也可以使用相同的钩子：

    var chatModel = OpenAiChatModel.builder()
    .options(OpenAiChatOptions.builder().model("gpt-4o").build())
    .httpClientBuilderCustomizer(myCustomizer)
    .build();

    在与 OpenAI 兼容的服务器中使用额外参数

    与 OpenAI 兼容的推理服务器（如 vLLM、Ollama 等）通常支持超出 OpenAI 标准 API 定义的额外参数。 例如，这些服务器可能会接受诸如 top_k、repetition_penalty 或其他官方 OpenAI API 无法识别的采样控制参数。

    extraBody 选项允许您向这些服务器传递任意参数。 在 extraBody 中提供的任何键值对都将包含在 JSON 请求的顶层，让您在调用 Spring AI 的 OpenAI 客户端时能够利用特定服务器的功能。

    extraBody 参数旨在用于与兼容 OpenAI 的服务器配合使用，而非官方 OpenAI API。 官方 OpenAI API 执行严格的验证，如果遇到无法识别的字段，将返回 HTTP 400 错误 ("Unknown parameter: 'extra_body'")。

    如果您正在与官方 OpenAI API 进行通信，您绝不应该填充 extraBody 参数。

    同时请注意，extraBody Map 在序列化过程中会被有意平铺到 JSON 请求的顶层。因此，设置 extraBody(Map.of("custom_flag", true)) 将导致 JSON 负载的根部出现 {"custom_flag": true}，这与官方 SDK 的行为一致。

    带属性的配置

    您可以使用 Spring Boot 属性来配置额外参数。 spring.ai.openai.chat.extra-body 下的每个属性都将成为请求中的顶级参数：

    spring.ai.openai.base-url=http://localhost:8000
spring.ai.openai.chat.model=meta-llama/Llama-3-8B-Instruct
spring.ai.openai.chat.temperature=0.7
spring.ai.openai.chat.extra-body.top_k=50
spring.ai.openai.chat.extra-body.repetition_penalty=1.1

    此配置将生成如下 JSON 请求：

    {
  "model": "meta-llama/Llama-3-8B-Instruct",
  "temperature": 0.7,
  "top_k": 50,
  "repetition_penalty": 1.1,
  "messages": [...]
}

    使用 Builder 的运行时配置

    ChatResponse response = chatModel.call(

        "Tell me a creative story",
        OpenAiChatOptions.builder()
            .model("meta-llama/Llama-3-8B-Instruct")
            .temperature(0.7)
            .extraBody(Map.of(
                "top_k", 50,
                "repetition_penalty", 1.1,
                "frequency_penalty", 0.5

            .build()
    ));

    spring.ai.openai.base-url=http://localhost:8000

    请参阅 vLLM 文档 以获取支持的采样参数完整列表。

    示例：Ollama 服务器

    在使用通过 OpenAI 兼容端点调用 Ollama 时，您可以传递 Ollama 特有的参数：

    OpenAiChatOptions options = OpenAiChatOptions.builder()
    .model("llama3.2")
    .extraBody(Map.of(
        "num_predict", 100,
        "top_k", 40,
        "repeat_penalty", 1.1
    ))
    .build();

ChatResponse response = chatModel.call(new Prompt("Generate text", options));

    请查阅 Ollama API 文档 以获取可用参数。

    extraBody 参数接受任何 Map<String, Object>，允许您传递目标服务器支持的任何参数。 Spring AI 不会对这些参数进行校验——它们将直接传递给服务器。 这种设计为处理各种兼容 OpenAI 的实现提供了最大的灵活性。

    来自推理模型的推理内容

    一些支持推理模型（例如 DeepSeek R1、带有推理解析器的 vLLM）的 OpenAI 兼容服务器，在其 API 响应中通过 reasoning_content 字段公开模型的内部思维链。 该字段包含模型用于得出最终答案的逐步推理过程。

    Spring AI 将 JSON 响应中的此字段映射到 AssistantMessage 元数据中的 reasoningContent 键。

    关于 reasoning_content 可用性的重要区别：

    • OpenAI 兼容服务器（DeepSeek、vLLM）：在 Chat Completions API 响应中暴露 reasoning_content ✅

    • OpenAI 官方模型 (GPT-5, o1, o3)：不要在 Chat Completions API 响应中暴露推理文本 ❌

    官方 OpenAI 推理模型在调用 Chat Completions API 时会隐藏思维链（chain-of-thought）内容。 它们仅在使用统计中暴露 reasoning_tokens 数量。 若要获取来自官方 OpenAI 模型的实际推理文本，您必须使用 OpenAI 的 Responses API（这是一个目前由本客户端不支持的独立端点）。

    回退行为：当服务器未提供 reasoning_content 时（例如官方的 OpenAI Chat Completions），reasoningContent 元数据字段将为空字符串。

    访问推理内容

    当使用兼容的服务器时，您可以从响应元数据中获取推理内容。

    直接使用 ChatModel：

    // Configure to use DeepSeek R1 or vLLM with a reasoning model
ChatResponse response = chatModel.call(
    new Prompt("Which number is larger: 9.11 or 9.8?")
);

// Get the assistant message
AssistantMessage message = response.getResult().getOutput();

// Access the reasoning content from metadata
String reasoning = message.getMetadata().get("reasoningContent");
if (reasoning != null && !reasoning.isEmpty()) {
    System.out.println("Model's reasoning process:");
    System.out.println(reasoning);
}

// The final answer is in the regular content
System.out.println("\nFinal answer:");
System.out.println(message.getContent());

    使用 ChatClient：

    ChatClient chatClient = ChatClient.create(chatModel);

String result = chatClient.prompt()
    .user("Which number is larger: 9.11 or 9.8?")
    .call()
    .chatResponse()
    .getResult()
    .getOutput()
    .getContent();

// To access reasoning content with ChatClient, retrieve the full response
ChatResponse response = chatClient.prompt()
    .user("Which number is larger: 9.11 or 9.8?")
    .call()
    .chatResponse();

AssistantMessage message = response.getResult().getOutput();
String reasoning = message.getMetadata().get("reasoningContent");

    流式推理内容

    在使用流式响应时，推理内容与普通消息内容一样，是按块（chunks）累积的：

    Flux<ChatResponse> responseFlux = chatModel.stream(
    new Prompt("Solve this logic puzzle...")
);

StringBuilder reasoning = new StringBuilder();
StringBuilder answer = new StringBuilder();

responseFlux.subscribe(chunk -> {
    AssistantMessage message = chunk.getResult().getOutput();

    // Accumulate reasoning if present
    String reasoningChunk = message.getMetadata().get("reasoningContent");
    if (reasoningChunk != null) {
        reasoning.append(reasoningChunk);
    }

    // Accumulate the final answer
    if (message.getContent() != null) {
        answer.append(message.getContent());
    }
});

    示例：DeepSeek R1

    DeepSeek R1 是一个能够展示其内部推理过程的推理模型：

    spring.ai.openai.api-key=${DEEPSEEK_API_KEY}
spring.ai.openai.base-url=https://api.deepseek.com
spring.ai.openai.chat.model=deepseek-reasoner

    当您向 DeepSeek R1 发送请求时，响应将同时包含推理内容（模型的思考过程）和最终答案。

    请参阅 DeepSeek API documentation 以获取有关推理模型的更多详情。

    示例：带有推理解析器的 vLLM

    当配置了推理解析器（reasoning parser）时，vLLM 支持推理模型：

    vllm serve deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B \
    --enable-reasoning \
    --reasoning-parser deepseek_r1
    spring.ai.openai.base-url=http://localhost:8000
spring.ai.openai.chat.model=deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B

    请参阅 vLLM 推理输出文档 以获取支持的推理模型和解析器。

    reasoning_content 的可用性完全取决于您使用的推理服务器。 并非所有兼容 OpenAI 的服务器都会暴露推理内容，即使是在使用具备推理能力的模型时也是如此。 请始终参考您服务器的 API 文档，以了解响应中包含哪些字段。

    OpenAI 兼容提供商的工具调用附加属性

    一些兼容 OpenAI 的提供商会在其响应中的 tool-call 对象中附加额外的字段。 一个常见的例子是 Google Gemini 的 OpenAI 兼容端点，它返回一个用于多轮工具调用的 thought_signature 字段：

    {
  "tool_calls": [
    {
      "id": "call_1",
      "type": "function",
      "function": { "name": "get_weather", "arguments": "{\"location\":\"Seoul\"}" },
      "extra_content": { "google": { "thought_signature": "..." } }
    }
  ]
}

    如果后续请求中缺少这些特定于提供商的字段，某些模型会拒绝工具调用历史记录。

    Spring AI 会自动捕获提供商响应中工具调用对象（tool-call objects）上的任何额外字段，并在助手消息包含在后续请求中时原样重放这些字段。 无需任何配置——该行为对于阻塞式和流式流程都是透明的。

    这仅适用于 tool-call 对象本身上的额外字段。 嵌套的 function 对象内部的额外字段不会被保留。
