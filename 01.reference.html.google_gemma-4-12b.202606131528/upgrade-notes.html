    更新日志

    升级到 2.0.0

    本章节涵盖了从 Spring AI 1.1.x 升级到 2.0.0 时所有的重大变更和迁移步骤。

    Advisors

    spring-ai-advisors-vector-store 重命名为 spring-ai-vector-store-advisor

    spring-ai-advisors-vector-store 模块已重命名为 spring-ai-vector-store-advisor，以更好地符合其他 Spring AI 模块的命名规范。

    ToolSearchToolCallingAdvisor 已移动到 spring-ai-tool-search-advisor

    ToolSearchToolCallingAdvisor 类已移动到专门的模块和包中：

    • 制品： spring-ai-tool-search-advisor（此前包含在 spring-ai-tool-search-tool 中）

    • Package: org.springframework.ai.chat.client.advisor.toolsearch (previously org.springframework.ai.tool.toolsearch.advisor)

    请相应地更新您的依赖项和导入语句：

    <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-tool-search-advisor</artifactId>
</dependency>

    新增：ToolSearchToolCallingAdvisor 自动配置与 Starter

    现在提供 Spring Boot 自动配置 (spring-ai-autoconfigure-tool-search-advisor) 和匹配的 starter (spring-ai-starter-tool-search-advisor)。 启用后，ToolSearchToolCallingAdvisor 将替换自动配置的 ChatClient 中的默认 ToolCallingAdvisor，将每次调用发送给 LLM 的工具定义限制为最相关的工具（通过关键词或语义搜索）。

    通过添加 starter 并设置属性来选择加入：

    <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-tool-search-advisor</artifactId>
</dependency>
    spring.ai.chat.client.tool-search-advisor.enabled=true

# Choose the index type: regex (default), lucene, or vector
spring.ai.chat.client.tool-search-advisor.tool-index-type=regex

    regex 索引不需要额外的依赖。 lucene 索引需要在类路径上包含 org.apache.lucene:lucene-core。 vector 索引需要一个 VectorStore 豆（类路径上需包含 spring-ai-vector-store）。

    变更：Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER 默认值

    Advisor.DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER 从 Ordered.HIGHEST_PRECEDENCE + 1000 更改为 Ordered.HIGHEST_PRECEDENCE + 200，将 memory advisors 置于其默认顺序，即位于 ToolCallingAdvisor (HIGHEST_PRECEDENCE + 300) 的外部)。

    ToolCallingAdvisor 现在默认在工具调用迭代过程中内部管理对话历史。记忆顾问（memory advisor）仅存储最终的用户/助手交互，绝不会将工具调用消息写入 ChatMemoryRepository。这是正确的默认设置，因为大多数仓库实现都不支持这些消息类型。

    如果您需要在循环内部使用内存（例如使用 InMemoryChatMemoryRepository），请显式地将 advisor 的顺序设置为高于 ToolCallingAdvisor.DEFAULT_ORDER，并调用 .disableInternalConversationHistory()：

    var toolCallingAdvisor = ToolCallingAdvisor.builder()
    .disableInternalConversationHistory()
    .build();
var chatMemoryAdvisor = MessageChatMemoryAdvisor.builder(chatMemory)
    .advisorOrder(Ordered.HIGHEST_PRECEDENCE + 400)
    .build();
    spring-ai-session 社区项目提供了一个具备会话感知能力的内存实现，它完全支持工具调用消息（tool-call messages），并可以在任何后端的工具调用循环中安全使用。它计划在 Spring AI 2.1 中取代 ChatMemory。详情请参阅 spring-ai-session 文档。

    工具调用

    Removed: internalToolExecutionEnabled from ToolCallingChatOptions

    internalToolExecutionEnabled 选项已从 ToolCallingChatOptions 以及所有特定供应商的 ChatOptions 类（例如 OpenAiChatOptions、AnthropicChatOptions）中移除。相应的 Spring Boot 配置属性 spring.ai.<provider>.chat.internal-tool-execution-enabled 也已被移除。

    Impact

    设置 .internalToolExecutionEnabled(false) 以选择加入用户控制的工具执行的代码将不再能编译。 设置 .internalToolExecutionEnabled(true)（显式启用内部循环）的代码将不再能编译，且其隐含的行为也不再存在——所有 ChatModel 实现中都已移除基于模型的内部工具执行。

    Migration

    移除所有对 .internalToolExecutionEnabled(…​) 的调用。推荐的方法是：

    • ToolCallingAdvisor 通过 ChatClient（推荐）—— 当存在工具时自动注册；无需标志。

    • 通过 ChatModel 直接控制用户循环 —— 只需调用 ChatModel 而不使用 ToolCallingAdvisor。工具调用不会自动执行；请自行检查 chatResponse.hasToolCalls() 并使用 ToolCallingManager 驱动循环。

    // Before
ChatOptions options = ToolCallingChatOptions.builder()
    .toolCallbacks(ToolCallbacks.from(new MyTools()))
    .internalToolExecutionEnabled(false)   // <-- remove this line
    .build();

// After
ChatOptions options = ToolCallingChatOptions.builder()
    .toolCallbacks(ToolCallbacks.from(new MyTools()))
    .build();

    Removed: ToolExecutionEligibilityPredicate and DefaultToolExecutionEligibilityPredicate

    ToolExecutionEligibilityPredicate（自 2.0.0 版本起已弃用）及其默认实现 DefaultToolExecutionEligibilityPredicate 已被移除。这些接口结合了基于选项的策略检查（internalToolExecutionEnabled）和响应检查（hasToolCalls()）。由于基于选项的标志已被移除，因此在 ChatModel 层级上没有替代方案。

    Migration

    如果您实现了 ToolExecutionEligibilityPredicate 来自定义工具执行的触发时机，请迁移到 ToolExecutionEligibilityChecker（见下文）并将其提供给 ToolCallingAdvisor。

    New: ToolExecutionEligibilityChecker in ToolCallingAdvisor

    ToolExecutionEligibilityChecker (Function<ChatResponse, Boolean>) 现在可以在 ToolCallingAdvisor.Builder 上进行设置，用于自定义工具调用循环的迭代时机。默认值为 chatResponse → chatResponse != null && chatResponse.hasToolCalls()。

    这是用于提供商特定停止原因逻辑（例如：除了检查工具调用是否存在，还检查完成原因）的扩展点：

    ToolCallingAdvisor advisor = ToolCallingAdvisor.builder()
    .toolExecutionEligibilityChecker(response ->
        response != null && response.hasToolCalls()
            && !"stop".equals(response.getResult().getMetadata().getFinishReason()))
    .build();

    Spring Boot 用户可以提供一个 ToolExecutionEligibilityChecker 类型的 bean；它将被自动配置的 ToolCallingAdvisor.Builder 自动识别：

    @Bean
ToolExecutionEligibilityChecker myChecker() {
    return response -> response != null && response.hasToolCalls();
}

    New: spring.ai.chat.client.tool-calling.enabled Property

    一个新的 spring.ai.chat.client.tool-calling.enabled 属性（默认值为 true）用于控制由自动配置的 ChatClient 是否自动注册 ToolCallingAdvisor。 将其设置为 false 可禁用所有调用的自动工具执行——工具仍作为定义发送给 AI 模型，但工具调用响应不会被自动执行。

    spring.ai.chat.client.tool-calling.enabled=false

    这是在每次单独调用时使用 AdvisorParams.toolCallingAdvisorAutoRegister(false) 的全局替代方案。

    移除：从 Advisor Builders 和 Auto-Configuration 中移除 streamToolCallResponses

    streamToolCallResponses 选项已从 ToolCallingAdvisor.Builder、ToolCallAdvisor.Builder 和 ToolSearchToolCallingAdvisor.Builder 中移除，同时也从它们对应的 Spring Boot 自动配置属性中移除：

    • spring.ai.chat.client.tool-calling.stream-tool-call-responses

    • spring.ai.chat.client.tool-search-advisor.stream-tool-call-responses

    Why

    当 streamToolCallResponses=true 时，中间的工具调用请求分片（tool-call request chunks）被流式传输到下游，但与之配对的 ToolResponseMessage（发送回 LLM 的响应）则没有。 任何记录了这些分片的下游内存顾问（memory advisor）都会收到一个没有对应工具响应的工具调用请求，从而导致对话历史损坏。 由于如果不引入破坏性变更（breaking change）到 ChatClientResponse 就无法修复此设计缺陷，因此该选项已被完全移除。

    Impact

    • 任何在 advisor builder 上调用 .streamToolCallResponses(true) 或 .streamToolCallResponses(false) 的代码都将无法通过编译。

    • 任何针对已移除属性的 application.properties 或 application.yml 条目都将被静默忽略。

    Migration

    从您的 builder 链中移除所有对 .streamToolCallResponses(…​) 的调用：

    // Before
var advisor = ToolCallingAdvisor.builder()
    .streamToolCallResponses(true)   // <-- remove this line
    .build();

// After
var advisor = ToolCallingAdvisor.builder().build();

    为了获取工具调用循环中每一次迭代的可视化信息——这也是 streamToolCallResponses=true 旨在解决的使用场景——请退出自动注册的 advisor，并使用 AdvisorParams.toolCallingAdvisorAutoRegister(false) 手动驱动循环：

    ToolCallingManager toolCallingManager = ToolCallingManager.builder().build();
ToolCallback[] tools = ToolCallbacks.from(new WeatherTools());
ChatOptions chatOptions = ToolCallingChatOptions.builder()
    .toolCallbacks(tools)
    .build();

String question = "What is the weather in Amsterdam and Paris?";
Prompt prompt = new Prompt(List.of(new UserMessage(question)), chatOptions);

ChatClientResponse response = chatClient.prompt()
    .user(question)
    .options(chatOptions)
    .advisors(AdvisorParams.toolCallingAdvisorAutoRegister(false))
    .call()
    .chatClientResponse();

while (response.chatResponse() != null && response.chatResponse().hasToolCalls()) {
    // inspect or forward the tool-call chunk here before executing
    ToolExecutionResult result = toolCallingManager.executeToolCalls(prompt, response.chatResponse());
    prompt = new Prompt(result.conversationHistory(), chatOptions);
    response = chatClient.prompt()
        .messages(result.conversationHistory())
        .options(chatOptions)
        .advisors(AdvisorParams.toolCallingAdvisorAutoRegister(false))
        .call()
        .chatClientResponse();
}
// forward or process the final answer here

    有关包含流式路径的完整示例，请参阅 User-Controlled Tool Execution — With ChatClient。

    JDBC Chat Memory sequence_id 列

    JdbcChatMemoryRepository 的架构增加了一个 sequence_id BIGINT 列，用于确定对话中的消息顺序。此前，排序依赖于 timestamp 列，但不同数据库的 TIMESTAMP 精度各不相同——在 MySQL 和 MariaDB 上，默认精度为一秒，因此在同一秒内保存的消息返回顺序是不确定的。而专门的整数序列可以在所有支持的数据库中保持一致的排序。

    保留了 timestamp 列。它现在存储消息的创建时间，并作为消息元数据中的 JdbcChatMemoryRepository.CONVERSATION_TS 键（类型为 java.time.Instant）进行暴露，以便应用程序可以显示消息的创建时间。时间戳在保存过程中得以保留：重新保存对话时，每条现有消息的原始创建时间都会被保留。

    Impact

    • SPRING_AI_CHAT_MEMORY 表新增了一个 sequence_id 列（类型为 BIGINT，在 Oracle 中为 NUMBER(19)，在 SQLite 中为 INTEGER）以及一个 SPRING_AI_CHAT_MEMORY_CONVERSATION_ID_SEQUENCE_ID_IDX 索引。timestamp 列及其索引保持不变。

    • 由 Spring AI 1.x 创建的现有表在生效前需要新增列，因为消息现在是按 sequence_id 排序的。

    • 从仓库中读取的消息现在在元数据中携带其创建时间戳。由于元数据不同，检索到的消息不再等于（Message.equals）在代码中构建的、除此之外完全相同的消息。通过值比较消息，或依赖于集合（sets）或映射（maps）中消息标识的代码应当考虑到这一点。

    Migration

    此更改是累加性的：添加新列并从现有的每会话订单（per-conversation order）中回填。数据不会丢失，且 timestamp 列保持不变。对于 PostgreSQL：

    ALTER TABLE SPRING_AI_CHAT_MEMORY ADD COLUMN sequence_id BIGINT;

WITH ordered AS (
    SELECT ctid, ROW_NUMBER() OVER (PARTITION BY conversation_id ORDER BY "timestamp") - 1 AS seq
    FROM SPRING_AI_CHAT_MEMORY
)
UPDATE SPRING_AI_CHAT_MEMORY t
SET sequence_id = o.seq
FROM ordered o
WHERE t.ctid = o.ctid;

ALTER TABLE SPRING_AI_CHAT_MEMORY ALTER COLUMN sequence_id SET NOT NULL;

CREATE INDEX SPRING_AI_CHAT_MEMORY_CONVERSATION_ID_SEQUENCE_ID_IDX
ON SPRING_AI_CHAT_MEMORY(conversation_id, sequence_id);

    根据您的数据库情况，调整标识符引用和行标识表达式（如上文中的 ctid）。ROW_NUMBER() OVER (PARTITION BY conversation_id ORDER BY <timestamp>) 模式可以在所有支持的引擎上重现现有的每条会话顺序。或者，由于聊天记忆保留的是最近的对话上下文而非永久历史，您可以根据更新后的 schema-<platform>.sql 脚本删除并重建表。

    选项不可变性与默认值

    选项的严格不可变性

    Options 类（如 ChatOptions、EmbeddingOptions 等）现在是严格不可变的。 选项中的集合（如 toolCallbacks、stopSequences、customHeaders）现在以不可变集合的形式存储。 此外，现在使用可空集合代替空集合，以更好地表示值的缺失。

    Impact

    • ChatOptions#copy() 和 *Options#fromOptions(*Options) 方法已被移除，因为选项现在是严格不可变的。

    • 修改由 options getter 返回的集合将抛出 UnsupportedOperationException。

    Migration

    若要创建 options 实例的修改副本，请使用 mutate() 方法，而不是 copy() 或 fromOptions()：

    // Before
OllamaChatOptions options = originalOptions.copy();
options.setFoo("...");

// After
OllamaChatOptions options = originalOptions.mutate()
        .foo("...")
        .build();

    默认值已移至 Options 构造函数

    选项的默认值（如默认模型名称、temperature 等）已从 Model 实现和 *Properties 配置类移动到选项构造函数本身。 *Properties 类中的默认配置属性已被移除，因为它们不再需要，且应与选项层级的默认值保持一致。

    Impact

    • ChatModel#getDefaultOptions() 已被弃用，请改用 ChatModel#getOptions()。

    • *Properties 类中的默认值不再重复。

    Migration

    在获取模型的默认选项时，请使用 getOptions() 代替 getDefaultOptions()：

    // Before
ChatOptions options = chatModel.getDefaultOptions();

// After
ChatOptions options = chatModel.getOptions();

    配置属性扁平化

    基于上述所述的聊天配置更改，所有其他模型（Embedding、Image、Audio、Moderation、OCR 等）的配置属性不再使用 .options 前缀。 例如，以前的 spring.ai.openai.embedding.options.model 现在变为 spring.ai.openai.embedding.model。 为了确保更平滑的迁移体验，提供了包含 .options 变体的弃用配置属性。

    Impact

    • *Properties 类中的 getOptions() 方法已弃用。

    • *Properties 中嵌套的 Options 类已弃用。

    • toOptions() 方法已从嵌套的 Options 类移动到根 *Properties 类。

    Migration

    更新您的 application.properties 或 application.yml，从属性键中移除 .options 段。

    # Before
spring.ai.openai.embedding.options.model=text-embedding-3-small

# After
spring.ai.openai.embedding.model=text-embedding-3-small

    在 Java 代码中，可以直接使用根属性类来访问选项，或者调用 toOptions()：

    // Before
String model = properties.getOptions().getModel();
OpenAiEmbeddingOptions options = properties.getOptions().toOptions();

// After
String model = properties.getModel();
OpenAiEmbeddingOptions options = properties.toOptions();

    在 Options Builders 中将 N() 重命名为 n()

    在各种 *Options 和配置属性类中，N() 构建方法已重命名为 n()，以符合 Java 命名规范。

    Impact

    • 任何调用这些 builder 上 .N(value) 的 Java 代码都将无法通过编译。

    Migration

    更新您的代码，改为调用 .n(value)。

    // Before
OpenAiChatOptions.builder().N(1).build();

// After
OpenAiChatOptions.builder().n(1).build();

    JSON 工具重构

    新增：JsonHelper 并更新了 JacksonUtils

    在 spring-ai-commons 中引入了一个新的 JsonHelper 类，作为执行 JSON 序列化和反序列化的标准方式。 它是可实例化的，并接受自定义的 JsonMapper，使得针对特定用例定制 JSON 行为变得非常简单。 JacksonUtils 获得了一个新的 getDefaultJsonMapper() 静态方法，该方法返回一个共享的、预配置好的 JsonMapper 实例。

    JsonHelper 将此前分散在 JsonParser、ModelOptionsUtils 和 McpJsonParser 中的 JSON 操作集中到了一个地方。 默认构造函数使用来自 JacksonUtils.getDefaultJsonMapper() 的共享映射器。 如果您需要不同的序列化设置，请注入自定义的 JsonMapper：

    // Default — uses the shared JsonMapper from JacksonUtils
JsonHelper jsonHelper = new JsonHelper();

// Custom — supply your own JsonMapper
JsonMapper myMapper = JsonMapper.builder()
    .addModule(new JavaTimeModule())
    .build();
JsonHelper customHelper = new JsonHelper(myMapper);

    Deprecated: JsonParser

    JsonParser（位于 org.springframework.ai.util.json）已被标记为即将移除。所有方法现在都委托给 JsonHelper。

    Impact

    调用 JsonParser 方法的代码在编译时会看到弃用警告。

    Migration

    JacksonUtils.getDefaultJsonMapper()

    JsonParser.fromJson(json, MyType.class)

    jsonHelper.fromJson(json, MyType.class)

    JsonParser.fromJson(json, type)

    jsonHelper.fromJson(json, type)

    JsonParser.toJson(object)

    jsonHelper.toJson(object)

    JsonParser.toTypedObject(value, type)

    jsonHelper.convertToTypedObject(value, type)

    ChatClient 工具调用

    Automatic ToolCallingAdvisor Registration

    ChatClient 现在总是会自动在顾问链中注册一个 ToolCallingAdvisor（除非显式禁用），因此无论工具是静态配置的，还是在运行时由另一个顾问注入的，模型请求的工具调用都会被自动处理。

    Impact

    现有的已经显式添加了 ToolCallingAdvisor 的代码，会导致链中出现两个该 advisor —— 一个来自显式添加，另一个来自自动注册。

    Migration

    从链中移除显式的 ToolCallingAdvisor，并让自动注册来处理它。如果您需要自定义配置，可以在 ChatClient 构建时提供预配置的 ToolCallingAdvisor.Builder（参见 Customizing the Default ToolCallingAdvisor 部分），或者禁用自动注册并手动注册该 advisor：

    // Before — manual registration
chatClient.prompt("What's the weather?")
    .tools(weatherTool)
    .advisors(ToolCallingAdvisor.builder().build())
    .call().content();

// After — auto-registration handles it; no explicit advisor needed
chatClient.prompt("What's the weather?")
    .tools(weatherTool)
    .call().content();

// Or, to keep full control, disable auto-registration explicitly
chatClient.prompt("What's the weather?")
    .tools(weatherTool)
    .advisors(
        AdvisorParams.toolCallingAdvisorAutoRegister(false),
        ToolCallingAdvisor.builder().build()
    )
    .call().content();

    新增：ToolAdvisor 标记接口

    添加了一个 ToolAdvisor 标记接口。ToolCallingAdvisor 实现了该接口。DefaultChatClient 会检查此标记以决定是否自动注册 ToolCallingAdvisor —— 如果链中的任何顾问已经实现了 ToolAdvisor，则跳过自动注册。

    拥有工具调用生命周期（tool-call lifecycle）的自定义顾问应实现 ToolAdvisor，以防止自动添加重复的 ToolCallingAdvisor。

    新增：MemoryAdvisor 标记接口

    添加了一个 MemoryAdvisor 标记接口。BaseChatMemoryAdvisor 现在继承了该接口。DefaultChatClient 使用此标记来检测下游的 memory advisors，并在存在此类 advisor 时禁用 `ToolCallingAdvisor` 的内部对话历史。

    未继承 BaseChatMemoryAdvisor 但需要与工具调用自动注册逻辑集成的自定义内存顾问（memory advisors）应当实现 MemoryAdvisor。

    新增：用于自定义 ToolCallingAdvisor 配置的 ChatClient.builder() 重载

    一个新的包含 5 个参数的 ChatClient.builder() 静态方法以及与之匹配的 DefaultChatClientBuilder 构造函数接受一个 ToolCallingAdvisor.Builder<?>，用于配置自动注册过程中使用的 advisor：

    ChatClient chatClient = ChatClient
    .builder(chatModel, observationRegistry, null, null,
            ToolCallingAdvisor.builder().toolCallingManager(myToolCallingManager))
    .build();

    Spring Boot 用户应优先选择以下其中一种：

    • 设置 spring.ai.chat.client.tool-calling.advisor-order 以控制 advisor 在链中的位置。

    • 声明一个 ToolCallingAdvisor.Builder<?> 类型的 bean，以完全替换自动配置的 builder（该 builder 已通过 @ConditionalOnMissingBean 被抑制）。

    移除：ChatClient 中的 ToolSpec 消费端 API

    tools(Consumer<ToolSpec>) / defaultTools(Consumer<ToolSpec>) API 和 ChatClient.ToolSpec 接口已被移除。现在的 tools(Object…​) / defaultTools(Object…​) 方法可以直接接受 ToolCallback、ToolCallbackProvider、带有 @Tool 注解的 POJO 实例，以及这些类型的集合或数组。上下文通过专门的 toolContext() / defaultToolContext() 方法单独设置。

chatClient.prompt()
    .tools(t -> t.callbacks(myCallback).context("tenantId", "acme"))
    .call().content();

// After
chatClient.prompt()
    .tools(myCallback)
    .toolContext(Map.of("tenantId", "acme"))
    .call().content();

    修改：MethodToolCallbackProvider 抛出 IllegalArgumentException 而不是 IllegalStateException

    MethodToolCallbackProvider 现在在两种情况下抛出 IllegalArgumentException（而不是 IllegalStateException）：

    • 当一个工具对象没有任何带有 @Tool 注解的方法时。

    • 当多个工具对象产生具有重复名称的回调函数时。

    Impact

try {
    ToolCallbacks.from(myObject);
}

// After
try {

    Migration

    直接声明 ToolCallback 类型的 bean，而不是原始的函数式 bean：

    // Before — bare Function bean resolved by name at runtime
@Bean
@Description("Get the weather in location")
Function<WeatherRequest, WeatherResponse> currentWeather() {
    return weatherService::getWeather;
}

// After — explicit ToolCallback bean

        .inputType(WeatherRequest.class)
        .build();

    BeanOutputConverter JSON Schema 生成

    BeanOutputConverter 现在将 JSON Schema 生成委托给 JsonSchemaGenerator，使结构化输出转换与工具调用中使用的 JSON Schema 行为保持一致。

    Impact

    • 在主构造函数中可选的 Kotlin 属性（可空或带有默认值的）不再包含在 JSON Schema 的 required 数组中。

    • 被标注为 @JsonProperty(required = false) 的属性，包括未指定 required 属性的 @JsonProperty 声明，不再被视为必填项。

    • 生成的 schema 现在包含符合 OpenAPI 风格的基础类型 format 提示（例如，int 为 int32，long 为 int64，LocalDateTime 为 date-time），与工具调用所使用的格式规范保持一致。

    • BeanOutputConverter.postProcessSchema(JsonNode) 扩展点已被移除。覆盖此方法的自定义子类将无法通过编译。

    Migration

    若要自定义 JSON Schema 生成，请改为重写 BeanOutputConverter.generateSchema()。子类可以通过委托给 super.generateSchema() 来对默认 Schema 进行后处理。

    // Before
class CustomConverter extends BeanOutputConverter<MyType> {

    CustomConverter() {
        super(MyType.class);
    }

    @Override
    protected void postProcessSchema(JsonNode schema) {
        // mutate schema
    }
}

// After
class CustomConverter extends BeanOutputConverter<MyType> {

    CustomConverter() {
        super(MyType.class);
    }

    @Override
    protected String generateSchema() {
        String schema = super.generateSchema();
        // post-process schema
        return schema;
    }
}

    Impact

    先前接受松散类型或缺失工具参数的现有 MCP 服务器，现在可能会对发送不符合规范参数的客户端返回验证错误。

    确保您的工具定义包含准确的 JSON schema，并确保所有客户端发送符合规范的参数。 若要禁用验证并恢复 2.0 之前的行为，请在服务器构建器上设置 validateToolInputs(false)：

    McpServer.sync(transportProvider)
    .validateToolInputs(false)
    .tool(myTool, handler)
    .build();

    McpSchema.Tool.inputSchema()（以及 outputSchema()）现在返回 Map<String, Object>，而不是之前的 JsonSchema 记录。 这允许任意 JSON Schema 方言关键字（如 $ref、unevaluatedProperties、厂商扩展）在往返传输过程中不被裁剪。

    Impact

    使用 tool.inputSchema() 作为 JsonSchema 对象的代码将无法编译。

    Migration

    切换到 Map<String, Object>：

    // Before
McpSchema.JsonSchema schema = tool.inputSchema();

// After
Map<String, Object> schema = tool.inputSchema();

    在使用 McpSchema.Tool.Builder 构建工具时，为了向后兼容，仍可使用已弃用的 inputSchema(JsonSchema) 辅助方法，但建议优先使用 inputSchema(Map) 或 inputSchema(McpJsonMapper, String)。

    使用 @McpTool 注解或 Spring AI 的 SyncMcpToolProvider / AsyncMcpToolProvider 的应用程序不受影响 —— Spring AI 会在内部处理架构生成。

    Replace customizeRequest() with httpRequestCustomizer() (sync) or asyncHttpRequestCustomizer() (async):

HttpClientSseClientTransport.builder(baseUrl)

// After
HttpClientSseClientTransport.builder(baseUrl)
    .httpRequestCustomizer(req -> req.header("Authorization", "Bearer token"))
    .build();

    以下接口不再是 sealed>： McpSchema.JSONRPCMessage, McpSchema.Request, McpSchema.Result, McpSchema.Notification, McpSchema.ResourceContents, McpSchema.CompleteReference, 以及 McpSchema.Content。

    Impact

    case McpSchema.ImageContent ic  -> "[image]";
    case McpSchema.EmbeddedResource er -> "[resource]";

// After
String text = switch (content) {
    case McpSchema.TextContent tc   -> tc.text();
    case McpSchema.ImageContent ic  -> "[image]";
    case McpSchema.EmbeddedResource er -> "[resource]";
    default -> throw new IllegalArgumentException("Unknown content type: " + content);

    对话历史已从工具上下文（ToolContext）中移除

    对话历史不再自动添加到 ToolContext 中。TOOL_CALL_HISTORY 常量和 getToolCallHistory() 方法已从 ToolContext 类中移除。

    Impact

    • ToolContext.TOOL_CALL_HISTORY 常量不再存在

    • ToolContext.getToolCallHistory() 方法已不存在

    • ToolContext 中的对话历史不再自动填充

    为什么要进行此更改？

    1. 内存效率：防止在长对话中出现无限制的内存增长

    2. 关注点分离：工具应当仅作用于其参数，而不应管理对话状态

    3. 架构对齐：对话上下文应属于顾问层级，而非工具执行层级

    Migration

    如果您的应用程序需要对话历史管理，请使用 ToolCallingAdvisor：

    使用 ToolCallingAdvisor 管理对话历史
    ChatClient chatClient = ChatClient.builder()
    .defaultAdvisors(
        ToolCallingAdvisor.builder()
            .conversationHistoryEnabled(true)  // Full history (default)
            .build()
    )
    .build();

    ToolCallingAdvisor 的工作原理：

    ToolCallingAdvisor 在顾问级别管理对话历史：

    • conversationHistoryEnabled=true（默认）：维护并发送完整的对话历史记录到 LLM 的工具调用迭代之间，允许 LLM 在完整上下文的基础上综合结果。

    • conversationHistoryEnabled=false：仅将最近的一次工具响应发送给 LLM（当 ChatMemory 顾问单独管理历史记录时非常有用）

    关键点：对话历史由LLM用于理解上下文并构建回复，而非由工具本身使用。工具仅接收其输入参数以及您明确提供的任何自定义上下文。

    工具中的自定义上下文：

    ToolContext 仍可用于向工具传递自定义的、特定于应用程序的数据：

    向工具传递自定义上下文
    ChatResponse response = chatClient.prompt()
    .user("What's the weather in SF?")
    .toolContext(Map.of("userId", "user123", "apiKey", "secret"))
    .call()
    .chatResponse();

    示例流程：

    1. 用户问：“旧金山和洛杉矶的天气怎么样？”

    2. LLM 请求工具调用：getWeather(SF) 和 getWeather(LA)

    3. 工具仅根据其参数执行（不包含对话历史）

    4. ToolCallingAdvisor 收集工具结果和对话历史

    5. LLM 从顾问处接收对话上下文并综合得出：“SF 的天气是 72°F，LA 的天气是 85°F”

    LLM 通过 advisor chain 而非 ToolContext 查看完整的对话。

    Testcontainers 类重命名：OpensearchContainer → OpenSearchContainer（正确的驼峰式命名法）

    Spring AI 的内部实现已更新，以自动处理这些变更。

    AbstractFilterExpressionConverter: doSingleValue 现在是抽象的

    在 AbstractFilterExpressionConverter（用于向量存储过滤表达式转换器）中，方法 doSingleValue(Object value, StringBuilder context) 已从具体方法更改为抽象方法。继承自 AbstractFilterExpressionConverter 的自定义向量存储实现现在必须显式实现此方法。

    Impact

    • 任何继承自 AbstractFilterExpressionConverter 且未重写 doSingleValue() 的自定义 FilterExpressionConverter 都将无法通过编译。

    • 实现类必须将单个过滤值（String、Number、Boolean、Date 等）转换为目标格式，并将其追加到提供的 StringBuilder 上下文中。

    Migration

    在您的自定义转换器中实现 doSingleValue(Object value, StringBuilder context)。您可以使用提供的静态辅助方法：

    • 基于 JSON 的过滤器（例如 PostgreSQL JSONPath、Neo4j Cypher、Weaviate）：使用 emitJsonValue(Object value, StringBuilder context) 对值进行序列化，并确保正确的引号和转义。

    • 基于 Lucene 的过滤器（例如 Elasticsearch、OpenSearch、GemFire）：对于字符串值，使用 emitLuceneString(String value, StringBuilder context)，并根据您存储库的查询语法处理其他类型（数字、布尔值、日期）。

    • 其他格式：实现您自己的逻辑并将结果追加到 context> 中。

    框架在调用 doSingleValue 之前会对值进行规范化（例如将 ISO 日期字符串转换为 Date），因此您的实现将接收到已经过规范化的值。如果您需要在标准流程之外构建表达式时进行相同的规范化，可以使用静态辅助函数 normalizeDateString(Object)。

    修复了 MongoDB Chat Memory 中的消息排序问题

    MongoChatMemoryRepository 已修复，现在按发送顺序（从旧到新）返回消息，与其他所有聊天记忆仓库的实现保持一致。此前，它错误地以相反顺序（从新到旧）返回消息，导致 LLM 的对话流中断。

    Impact

    如果您的应用程序之前使用的是 MongoChatMemoryRepository 并通过某种变通方法（例如在检索后反转消息顺序）来处理错误的排序问题，您需要移除该变通方法。

    Migration

    移除任何在从 MongoDB 聊天记忆中检索后反转消息顺序的代码：

List<Message> messages = chatMemoryRepository.findByConversationId(conversationId);
Collections.reverse(messages); // Remove this workaround

// AFTER (correct ordering):
List<Message> messages = chatMemoryRepository.findByConversationId(conversationId);
// Messages are now correctly ordered chronologically

    所有聊天记忆仓库现在都一致地按发送顺序（从旧到新）返回消息，这是大语言模型对话历史的预期格式。

    开发阶段服务

    Spring AI 自动配置组件的变更

    工具调用中 FunctionCallingOptions 用法的变更

    每个 ChatModel 实例在构造时，可以接受一个可选的 ChatOptions 或 FunctionCallingOptions 实例，用于配置调用模型时使用的默认工具。

    在 1.0.0-M6 之前：

    • 通过默认 FunctionCallingOptions 实例的 functions() 方法传递的任何工具都包含在从该 ChatModel 实例发出的每次模型调用中，且可能会被运行时选项覆盖。

    • 通过默认 FunctionCallingOptions 实例的 functionCallbacks() 方法传递的任何工具仅用于运行时动态解析（参见 Tool Resolution），除非明确请求，否则永远不会包含在任何对模型的调用中。

    从 1.0.0-M6 开始：

    • 任何通过 functions() 方法或默认 FunctionCallingOptions 实例的 functionCallbacks() 传递的工具现在都以相同的方式处理：它们将被包含在从该 ChatModel 实例发出的每次模型调用中，并可能被运行时选项覆盖。由此一来，工具在模型调用中的包含方式保持了一致性，并防止了因 functionCallbacks() 与所有其他选项之间的行为差异而产生的任何混淆。

    如果您希望让一个工具可用于运行时动态解析，并且仅在模型明确请求时才将其包含在聊天请求中，您可以使用 Tool Resolution 中描述的策略之一。

    1.0.0-M6 引入了用于处理工具调用（tool calling）的新 API。除了上述描述的情况外，旧版 API 在所有场景下均保持向后兼容。旧版 API 仍可使用，但已被弃用，并将在 1.0.0-M7 中移除。
